jawelte is a thin core wrapped in a constellation of modules. Each module is one feature jawelte tests need to integrate — JPA, JTA, JAX-RS, EJB scopes, WireMock, batch jobs, Spring Data, content-diff assertions, … — packaged as an opt-in dependency that plugs into core's port surface. Adding a module is the same act as adding any other Maven dependency to your test scope; no global wiring file, no module registration step. Each module owns its own ports (api) and adapter (impl), so swapping the implementation, hooking events, or overriding a default is the same hexagonal pattern jawelte's core documents.

This page opens with the catalog of what every module is and what it gives you. The cdi-module section below it goes deeper — the rest of the modules will land here over time, each as its own section using the same template.

1. modules overview

Twelve modules ship with jawelte today. Pick the ones that match your stack; the rest stay off the classpath and out of your test runtime entirely. cdi-module is the one foundational pairing — everything else is optional.

cdi-modulefoundational

The default partner of core. Gives you the full @EnableTestBeans experience: a CDI container around every test class, automatic Mockito mocks for collaborators that live outside your module's boundary (the contract is on your classpath, the implementation isn't — jawelte fills the gap), and a clean shutdown when the test finishes. Every example in the core docs assumes cdi-module is on your classpath. Details below.

scope-moduleopt-in

Two new CDI scopes tuned for tests — @TestMethodScoped (lives for one @Test method) and @TestClassScoped (lives for one test class). Drop them on your beans and stop worrying about state bleeding between tests. Read the details →

jpa-moduleopt-in

Inject an EntityManager into your code, save and query entities, let jawelte clean up between methods. The EntityManagerFactory boots once per JVM (so there's no slow per-test ramp); the EntityManager itself is transaction-scoped, table cleanup runs automatically, and read-only data marking is one annotation away. Read the details →

jta-moduleopt-in

Add this and your @Transactional code starts running inside a real JTA transaction. Geronimo, Narayana, or Atomikos — pick whichever fits your project by putting the matching transaction-manager on the test classpath. The right module for multi-resource setups or anything that won't work under plain JPA RESOURCE_LOCAL. Read the details →

ejb-moduleopt-in

Test EJB-annotated production code without needing an application server. @Stateless and @Singleton beans get mapped to CDI scopes plus an implicit transaction — your code keeps the EJB annotations, your test runs in plain CDI SE. Not a 1:1 emulation of a real container (no pooling, no remoting, no full container-managed-transaction semantics across multiple resources), but for the kind of EJB code most projects ship it covers the common ground.

jaxrs-moduleopt-in

Test your REST endpoints with a real HTTP server inside the test JVM. Annotate the class with @EnableJaxRs, inject the live base URL, hit your endpoints over the wire just like a client would. Works with CXF or RESTEasy — pick whichever JAX-RS implementation your project already uses.

testcontrol-moduleopt-in

One annotation per test method that wires the whole fixture in: load these datasets, scope these beans, expect this end-state. @TestControl turns what would be a noisy setup block into a single declarative line.

db-testdata-moduleopt-in

Load database fixtures in one fluent call and assert the end-state with a diff that names the exact row and column that changed. Built on DbUnit, accepts both raw JDBC connections and JPA persistence units.

content-diff-moduleopt-in

Compare JSON and XML payloads by meaning, not byte-for-byte. When the assertion fails you get a list of every mismatched path with the line number of the expected document — no more squinting at giant string diffs.

wiremock-moduleopt-in

WireMock servers as injectable CDI beans. Annotate the test with @EnableWireMock, @Inject a WireMockServer, stub the upstream HTTP your code calls. One qualifier per endpoint when you have several to mock at once.

spring-data-moduleopt-in

Use Spring Data repositories in a CDI test without a Spring context. Add the dependency and your repository interfaces become CDI beans backed by the same EntityManager jpa-module hands out.

batch-moduleopt-in

Run a Jakarta Batch (jBatch) job from your test and assert on the outcome. Fire one event, jawelte drives the job to completion synchronously, and your test sees the final status — no polling, no threading dance.

2. cdi-module

2.1 purpose

cdi-module is the SE-CDI adapter behind every example in docs/core.html. It implements core's single-impl TestBeanContainerPort with CdiTestBeanContainer — that's the class that boots the SE container in beforeAll, populates @Inject fields in postProcessTestInstance, activates the request scope in beforeEach, and shuts the container down in afterAll. The runtime under the hood is OpenWebBeans or Weld — whichever SE container artifact is on your test classpath; the rest of jawelte never sees that choice.

On top of the container lifecycle, cdi-module ships a CDI extension (TestBeansCdiExtension) that scans the test class for @TestBean declarations, synthesises CDI beans for inline-mock fields and unsatisfied injection points, and wires the result into the bean archive. The user surface is the trio of annotations defined in core (@EnableTestBeans, @TestBean, @ConfigBean); cdi-module is what makes them DO something.

2.2 already in the core docs

Most user-facing cdi-module behaviour lives behind the core-docs annotations. The core docs already cover:

  • Hello-world — cdi-module booting the container and injecting a real bean.
  • Auto-mock — cdi-module's auto-mock extension filling unsatisfied @Inject sites with Mockito mocks, plus the lifecycle/scope discussion (one mock per (type, qualifier-set), fresh per test method).
  • @TestBean modes (alternative class, producer-method class, static field) — cdi-module is what resolves these.
  • @EnableTestBeans(limitToTestBeans=true) — cdi-module is what implements the whitelist veto.
  • @EnableTestBeans(manageContainer=false) — cdi-module is what skips the boot/shutdown when the test owns the container.
  • Events (ContainerStarted, BeforeScopeStarted) — cdi-module fires them.

If you're reading this page first, jump to those sections for the daily-use patterns. Everything below is the cdi-module-specific surface that didn't fit naturally into the core docs.

2.3 ports cdi-module ships

cdi-module ships four ports in cdi-module/api. Each follows the same shape as the core ports: an interface in api, a default impl in impl, override via ServiceLoader + @Priority.

MockFactory

Single active impl, ServiceLoader. Produces the object jawelte hands to CDI as the synthetic-bean instance for an auto-mocked injection point. The default MockitoMockFactory wraps Mockito.mock(Class) and returns null on any RuntimeException (so unmockable types like String drop through to CDI's normal unsatisfied-IP path). Override the port to use EasyMock, a hand-rolled fake factory, or any deterministic stub strategy — jawelte's auto-mock machinery routes through whatever MockFactory wins the priority resolution.

ExcludedPackageFilter

Single active impl, ServiceLoader. Decides whether a given owning bean's injection points should be considered for auto-mocking. cdi-module's DefaultExcludedPackageFilter reads the MP Config key org.os890.jawelte.module.cdi.auto-mock.exclude-owning-bean-packages and skips any owning bean whose class lives under one of those package prefixes. Used to keep the framework's own beans (Weld internals, SmallRye, OWB, DeltaSpike, …) from polluting your test's auto-mock surface.

WhitelistFilter

Single active impl, ServiceLoader. The dual of ExcludedPackageFilter for the limitToTestBeans=true mode — decides which framework-internal classes survive the whitelist veto. DefaultWhitelistFilter reads org.os890.jawelte.module.cdi.framework-allowlist.packages and lets through anything under those package prefixes (the JDK, the CDI runtime, MP Config, jawelte itself). Without this port the strict-mode would also veto jawelte's own bootstrap classes and break the test before it starts.

CdiContainerPort

Single active impl, ServiceLoader. The extension point for swapping out the SE container bootstrap itself. SeContainerCdiContainerPort is the default — calls SeContainerInitializer.newInstance().initialize(). Replace this port to bootstrap a different CDI container (a custom SE wrapper, a managed container with pre-configured beans, an ArC-based runtime in the future) without touching CdiTestBeanContainer itself. Most users never replace this port.

2.4 config keys

cdi-module reads four MP Config keys. The first three are owned by cdi-module and document the user-overridable knobs; the fourth (auto-mock.default-scope) is read by cdi-module but defaulted by scope-module when that module is on the classpath.

org.os890.jawelte.module.cdi.framework-allowlist.packages java., javax., jakarta., org.jboss.weld., org.apache.webbeans., org.apache.deltaspike., org.os890.jawelte.

Comma-separated package prefixes the DefaultWhitelistFilter always lets through, even in limitToTestBeans=true mode. Add your own framework prefixes here when shipping deeply-integrated libraries that need to stay visible to CDI during strict-mode tests.

org.os890.jawelte.module.cdi.auto-mock.exclude-owning-bean-packages org.jboss.weld., org.apache.webbeans., org.apache.deltaspike., io.smallrye.

Comma-separated package prefixes the DefaultExcludedPackageFilter skips when collecting unsatisfied injection points for auto-mocking. Stops jawelte from synthesising mocks for IPs owned by the CDI runtime / extensions themselves. ConfigKeyAliasProvider contributors (jpa-module, spring-data-module) push their own framework-private prefixes into this list at runtime.

org.os890.jawelte.module.cdi.auto-mock.exclude-packages — (no key by default; only contributor aliases via ConfigKeyAliasProvider)

User-defined package prefixes whose types should NOT receive an auto-mock when unsatisfied. The logical key for this concept; non-owning modules contribute additional package prefixes via ConfigKeyAliasProvider (see section 3.7 of the core docs). Set this key in your own microprofile-config.properties to opt one of your own packages out of auto-mocking.

org.os890.jawelte.module.cdi.auto-mock.default-scope org.jboss.weld… (unset by default; scope-module sets it to org.os890.jawelte.module.scope.api.TestMethodScoped)

The FQCN of the CDI scope annotation jawelte assigns to non-JDK auto-mock synthetic beans. cdi-module reads the key; the fallback when no value is configured is RequestScoped (matching the lifecycle described in the core docs). Pairing the test with scope-module rebinds it to TestMethodScoped automatically (scope-module's microprofile-config.properties sets the key at MP Config ordinal 100).

2.5 maven setup

Add cdi-module-api + cdi-module-impl to your test scope alongside core. A CDI runtime is needed too — either org.apache.openwebbeans:openwebbeans-se or org.jboss.weld.se:weld-se-shaded; pick the one your project already standardises on. The listings ship both as optional Maven profiles so you can see the pattern, but a single fixed dependency works equally well.

pom.xml fragmentlistings/01-hello-world/pom.xml
<dependency>
  <groupId>org.os890.jawelte</groupId>
  <artifactId>jawelte-cdi-module-api</artifactId>
  <version>${jawelte.version}</version>
  <scope>test</scope>
</dependency>
<dependency>
  <groupId>org.os890.jawelte</groupId>
  <artifactId>jawelte-cdi-module-impl</artifactId>
  <version>${jawelte.version}</version>
  <scope>test</scope>
</dependency>
<dependency>
  <groupId>org.mockito</groupId>
  <artifactId>mockito-core</artifactId>
  <version>${mockito.version}</version>
  <scope>test</scope>
</dependency>
<!-- one CDI runtime: openwebbeans-se OR weld-se-shaded -->

Mockito is technically only needed when auto-mocking is in use (the default MockFactory wraps it). A test that runs in limitToTestBeans=true mode and explicitly declares every bean it needs can skip the Mockito dep; in practice almost every test wants it.
