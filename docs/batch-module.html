batch-module fires a Jakarta Batch (jBatch) job through a single CDI event and blocks the test thread until the job reaches a terminal status. No polling loop, no Thread.sleep, no manual JobOperator wrangling — the synchronous observer in batch-module-impl does it all, populates the event with the final JobExecution, and unblocks fire(...) so the test reads the result off the same instance.

1. quick-start

1.1 purpose

Testing a Jakarta Batch job means: start it via JobOperator, get back an executionId, then poll until BatchStatus becomes terminal (COMPLETED / FAILED / STOPPED / ABANDONED) or your patience runs out. Every test reinvents the polling loop, the backoff strategy, and the timeout handling. batch-module collapses all of it into one fluent value class and one CDI Event.fire(...) call — the observer encapsulates the polling, the timeout, and the result wiring.

1.2 hello-world

One JSL job file, one batchlet class, one fire-and-assert test.

listing batch-module/01 · hello-worldlistings/batch-module/01-hello-world/
// src/test/resources/META-INF/batch-jobs/simple-job.xml
<job id="simple-job" xmlns="https://jakarta.ee/xml/ns/jakartaee" version="2.0">
    <step id="step1">
        <batchlet ref="simpleBatchlet"/>
    </step>
</job>

// SimpleBatchlet.java
@Named("simpleBatchlet")
@Dependent
public class SimpleBatchlet implements Batchlet {
    @Override public String process() { return "COMPLETED"; }
    @Override public void stop() {}
}

// HelloBatchTest.java
@EnableTestBeans
class HelloBatchTest {

    @Inject
    private Event<BatchExecution> batchEvent;

    @Test
    void simpleJobRunsToCompleted() {
        BatchExecution execution = new BatchExecution("simple-job");

        batchEvent.fire(execution);

        assertThat(execution.getStatus()).isEqualTo(BatchStatus.COMPLETED);
        assertThat(execution.getJobExecution()).isNotNull();
        assertThat(execution.getExecutionId())
                .isEqualTo(execution.getJobExecution().getExecutionId());
    }
}

@EnableTestBeans is the core-module JUnit extension that boots a CDI SE container around the test class — batch-module assumes it (and the cdi-module impl that backs it) is on the classpath. BatchStatus, JobOperator, JobContext and Batchlet are stock Jakarta Batch types from jakarta.batch-api.

2. detailed

2.1 BatchExecution — the request/result carrier

BatchExecution is a mutable value class that doubles as the request and result carrier. You instantiate it with the JSL job name, add parameters / a timeout, fire it — and when fire(...) returns, the same instance now holds the executionId and the JobExecution snapshot.

Builder methodWhat it sets
new BatchExecution("job-name")The JSL job-id to start. Empty / null throws IllegalArgumentException.
.param(key, value)Adds (or replaces) one job parameter. Cumulative.
.timeout(Duration)Overrides the default 60-second timeout.
Result accessorAvailable after fire returns
.getStatus()Terminal BatchStatus — COMPLETED / FAILED / STOPPED / ABANDONED.
.getExitStatus()Terminal exit-status string from the JSL contract.
.getJobExecution()Full JobExecution snapshot from JobOperator.
.getExecutionId()JobOperator-assigned executionId. Throws IllegalStateException if read before fire populated the event.
listing batch-module/02 · job-parameterslistings/batch-module/02-job-parameters/
// src/test/java/example/jobparams/EchoBatchlet.java
@Named("echoBatchlet")
@Dependent
public class EchoBatchlet implements Batchlet {

    @Inject
    private JobContext jobContext;

    @Inject
    private JobOperator jobOperator;

    @Override
    public String process() {
        // BatchExecution.param() values come back through
        // jobOperator.getParameters(executionId) — NOT
        // jobContext.getProperties() (which holds JSL <properties>).
        Properties parameters = jobOperator.getParameters(jobContext.getExecutionId());
        jobContext.setExitStatus(parameters.getProperty("greeting") + "=" + parameters.getProperty("target"));
        return "COMPLETED";
    }

    @Override
    public void stop() {
    }
}

// src/test/java/example/jobparams/JobParametersTest.java
@EnableTestBeans
class JobParametersTest {

    @Inject
    Event<BatchExecution> batchEvent;

    @Test
    void parametersAreVisibleToTheBatchletViaJobContext() {
        BatchExecution execution = new BatchExecution("parametrised-job")
                .param("greeting", "hello")
                .param("target", "world");

        batchEvent.fire(execution);

        assertThat(execution.getStatus()).isEqualTo(BatchStatus.COMPLETED);
        assertThat(execution.getExitStatus()).isEqualTo("hello=world");
    }
}

2.2 Event<BatchExecution>.fire — the blocking call

The CDI Event.fire(...) looks fire-and-forget but is observably blocking: the impl observer runs synchronously on the test thread, polls JobOperator with exponential backoff (50 ms initial, capped at 5 s) until a terminal BatchStatus is reached, then populates the BatchExecution with the final status and the resolved JobExecution handle before fire(...) returns. The test reads the result off the same instance that was fired — see listing 01 for the simplest shape (fire(...), then execution.getStatus()).

2.3 timeout

Default 60 seconds. If the job does not reach a terminal status in time, the default TimeoutHandler throws IllegalStateException — the job itself is not cancelled; it keeps running on the jBatch thread, just no longer observed by your test.

An alternative ships in batch-module-impl: PopulateLatestSnapshotTimeoutHandler populates the event with the latest observed JobExecution snapshot and returns without throwing. Activate it by shipping a custom src/test/resources/META-INF/services/org.os890.jawelte.module.batch.api.port.TimeoutHandler file (test classpath, not main) naming that class. See the SPI section for the priority rule.

listing batch-module/03 · timeout-handlerlistings/batch-module/03-timeout-handler/
// src/test/resources/META-INF/services/org.os890.jawelte.module.batch.api.port.TimeoutHandler
org.os890.jawelte.module.batch.impl.adapter.timeout.PopulateLatestSnapshotTimeoutHandler

// src/test/java/example/timeout/LongRunningBatchlet.java
@Named("longRunningBatchlet") @Dependent
public class LongRunningBatchlet implements Batchlet {
    @Override
    public String process() throws InterruptedException {
        Thread.sleep(3_000L);
        return "COMPLETED";
    }
    @Override public void stop() { }
}

// src/test/java/example/timeout/TimeoutHandlerTest.java
@Test
void alternativeHandlerPopulatesEventWithoutThrowing() {
    BatchExecution execution = new BatchExecution("long-running-job")
            .timeout(Duration.ofMillis(500L));

    assertThatCode(() -> batchEvent.fire(execution)).doesNotThrowAnyException();

    assertThat(execution.getJobExecution()).isNotNull();
    assertThat(execution.getStatus()).isNotEqualTo(BatchStatus.COMPLETED);
}

2.4 picking a jBatch runtime

batch-module talks to jBatch through the spec API (JobOperator, JobExecution, BatchStatus), so any conformant runtime works. Tested in jawelte's own sweep: Apache BatchEE (default; org.apache.batchee:batchee-jbatch) and JBeret (org.jberet:jberet-se). Pick by classpath dependency; no code change.

3. spi / port reference

batch-module ships one SPI port:

PortDefaultPurpose
TimeoutHandlerThrowOnTimeoutTimeoutHandler with @Priority(Integer.MAX_VALUE) — throws IllegalStateException when the timeout elapsesDecides what happens when the polling loop exceeds BatchExecution.getTimeout(): either throw (job didn't finish in time) or populate the event with the latest snapshot and return normally (here's what the runtime last reported).

Resolved via TestContext.loadService(TimeoutHandler.class); ServicePriorityResolver picks the implementation with the lowest numeric @Priority. To activate an alternative — including the in-impl PopulateLatestSnapshotTimeoutHandler — ship a src/test/resources/META-INF/services/org.os890.jawelte.module.batch.api.port.TimeoutHandler file naming the alternative impl's FQCN with a @Priority lower than Integer.MAX_VALUE. The lookup is cached in a static field for the JVM lifetime, so switching handlers mid-suite is not supported.

That's the only customization knob the module exposes. Everything else — the polling cadence (50 ms initial, exponential backoff to 5 s cap), the synchronous observer dispatch, the executionId / JobExecution result wiring — lives inside batch-module-impl and is not user-tunable.
