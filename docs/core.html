core is jawelte's contract layer. It turns JUnit 5 lifecycle hooks into your CDI container's lifecycle, defines the annotations test authors actually use (@EnableTestBeans, @TestBean, @ConfigBean), and ships the ports every other module plugs into. core does not ship a container. Pair it with cdi-module (the default adapter for OpenWebBeans / Weld SE) — every example on this page assumes that pairing.

Every code block on this page links to a runnable sample under listings/. Each sample is a stand-alone Maven project — copy a folder out of the repository and run mvn test on it without any other setup.

1. quick-start

1.1 purpose

core exposes a JUnit 5 extension (@EnableTestBeans) that boots a CDI container around your test class, populates @Inject fields on the test instance, activates the request scope around each test method, and tears everything down afterwards. The test author writes plain JUnit; jawelte does the wiring.

On top of the lifecycle, core defines three annotations the test author touches directly:

  • @EnableTestBeans — switches the extension on for a class; carries two options (limitToTestBeans, manageContainer) covered in section 2.1.
  • @TestBean — picks per-test-class bean replacements (alternative class, producer-method class, or a pre-built value via a static field). Covered in 2.2.
  • @ConfigBean — declares a typed configuration facade backed by jawelte's ConfigResolver. Covered in 2.3.

Two more layers sit underneath the annotations and matter once you're past hello-world:

  • Events — ContainerStarted, BeforeScopeStarted, AfterTestTransaction — fire at well-defined points and let module code react to the lifecycle.
  • Ports — the SPI surface every adapter plugs into (TestBeanContainerPort, TestModuleLifecyclePort, ConfigResolver, BeanScopeMapper, …). Section 3 walks them.

1.2 hello-world

A plain @ApplicationScoped bean in src/main, a JUnit test in src/test annotated @EnableTestBeans, one @Inject field, one assertion. That's the whole shape.

listing 01 · hello-worldlistings/01-hello-world/
// src/main/java/example/hello/HelloService.java
@ApplicationScoped
public class HelloService {
    public String greet(String name) {
        return "hello, " + name + "!";
    }
}

// src/test/java/example/hello/HelloServiceTest.java
@EnableTestBeans
class HelloServiceTest {

    @Inject
    HelloService helloService;

    @Test
    void greetsByName() {
        assertThat(helloService.greet("jawelte")).isEqualTo("hello, jawelte!");
    }
}

Run mvn test from inside the listing folder; one test passes in under a second. The CDI container booted by jawelte discovered HelloService, injected it into the test instance, ran the test method inside an active request scope, and shut down.

1.3 common use-cases

auto-mocked dependency

Production code @Injects a collaborator with no implementation on the classpath. jawelte's default MockFactory (a Mockito wrapper) supplies a mock; the test stubs it with plain Mockito.

listing 02 · auto-mocklistings/02-auto-mock/
// src/main/java/example/automock/Translator.java
public interface Translator { String translate(String value); }

// src/main/java/example/automock/Greeter.java
@ApplicationScoped
public class Greeter {

    @Inject
    Translator translator;

    public String greet(String name) {
        return "hello, " + translator.translate(name) + "!";
    }
}

// src/test/java/example/automock/GreeterTest.java
@EnableTestBeans
class GreeterTest {

    @Inject
    Greeter greeter;

    @Inject
    Translator translator;  // SAME auto-mock Greeter sees

    @Test
    void unsatisfiedDependencyIsAutoMocked() {
        when(translator.translate("jawelte")).thenReturn("JAWELTE");
        assertThat(greeter.greet("jawelte")).isEqualTo("hello, JAWELTE!");
    }
}

lifecycle & sharing of auto-mocks

Auto-mocks are @RequestScoped by default. jawelte registers exactly one synthetic bean per (target-type, qualifier-set) shape — every injection point matching that shape resolves to the same mock instance for the duration of the current test method. So Greeter.translator (held by the application-scoped production bean) and GreeterTest.translator (the test class field) point at the identical mock; when(translator…) on the test side stubs exactly what greeter.greet(…) reads on the production side.

The request scope is freshly activated in beforeEach and torn down in afterEach, so each test method gets its own fresh mock. Stubs you set up in one method never bleed into the next — Mockito state resets implicitly with the scope. Add a second @Test method that doesn't call when(…) and translator.translate(…) returns Mockito's default null again.

The default scope is configurable; the exact MP Config key and what each module rebinds it to is covered in the cdi-module / scope-module documentation. JDK types (String, primitives, the final classes mocking can't subclass…) are auto-mocked at @Dependent scope so each injection point gets its own instance — the framework can't put a normal-scope proxy on a final class.

Mockito version on JDK 25

The listing pins mockito-core 5.23.0 deliberately. Mockito's default inline mock maker rewrites bytecode at runtime via Byte Buddy; older Mockito releases (e.g. 5.14.2) bundled Byte Buddy 1.15.4, which only knows class files up to Java 24 (major version 68). Under JDK 25 (major 69), Mockito.mock(...) throws

java.lang.IllegalArgumentException: Java 25 (69) is not supported by the
current version of Byte Buddy which officially supports Java 24 (68)

jawelte's MockitoMockFactory catches the exception and returns null, the auto-mock synthetic bean is never registered, and @Inject Translator fails with UnsatisfiedResolutionException at container boot. Mockito 5.23.0 ships Byte Buddy 1.17.7, which understands Java 26's class file (major 70) and therefore Java 25 too — picking that version is enough; no mockito-extensions/org.mockito.plugins.MockMaker override and no -Dnet.bytebuddy.experimental=true JVM flag.

If you have to keep an older Mockito on the classpath (transitive dep clash, internal artifact-policy, …), the same fix can be applied by overriding only Byte Buddy: pin net.bytebuddy:byte-buddy + net.bytebuddy:byte-buddy-agent to 1.17.7 (or newer) in your <dependencyManagement>. The mock-maker-subclass config file route is the last-resort fallback when neither version bump is possible.

@TestBean — pick an alternative

A test-only @Alternative class wins over the production impl when its class is named in @TestBean(bean=…) on the test class.

listing 03 · test-bean-alternativelistings/03-test-bean-alternative/
// src/test/java/example/alt/StubEmailService.java
@Alternative
@ApplicationScoped
public class StubEmailService implements EmailService {

    @Override
    public String send(String to) {
        return "stub:" + to;
    }
}

// src/test/java/example/alt/EmailServiceTest.java
@EnableTestBeans
@TestBean(bean = StubEmailService.class)
class EmailServiceTest {

    @Inject
    EmailService emailService;

    @Test
    void picksTheStub() {
        assertThat(emailService.send("alice@example.com")).isEqualTo("stub:alice@example.com");
    }
}

@TestBean — pre-built value on a static field

Put @TestBean on a static final field whose initialiser yields the bean instance. No @Alternative, no producer — the field value IS the bean. Idiomatic for "register this exact object as the bean". The two static fields below show the two most common shapes side by side: a literal value (new Greeting(…)) and a Mockito mock (Mockito.mock(Clock.class)) wired in via the same static-field recipe.

listing 04 · test-bean-static-fieldlistings/04-test-bean-static-field/
// src/main/java/example/staticfield/Greeting.java
public record Greeting(String text) {
}

// src/main/java/example/staticfield/Clock.java
@FunctionalInterface
public interface Clock {
    Instant now();
}

// src/test/java/example/staticfield/GreetingTest.java
@EnableTestBeans
class GreetingTest {

    @TestBean
    public static final Greeting WELCOME_GREETING = new Greeting("hello-from-static-field");

    @TestBean
    public static final Clock CLOCK = mock(Clock.class);

    @Inject
    Greeting greeting;

    @Inject
    Clock clock;

    @Test
    void staticFieldLiteralBecomesTheBeanInstance() {
        assertThat(greeting).isSameAs(WELCOME_GREETING);
    }

    @Test
    void staticFieldMockitoMockIsInjectedAndStubbable() {
        Instant pinned = Instant.parse("2026-05-20T12:00:00Z");
        when(clock.now()).thenReturn(pinned);

        assertThat(clock).isSameAs(CLOCK);
        assertThat(clock.now()).isEqualTo(pinned);
    }
}

Both static-field declarations register their respective values once at class-load time — WELCOME_GREETING stays the same literal record across the whole test class; CLOCK stays the same Mockito mock instance, with stubs reset between methods by Mockito's @Singleton-scoped instance receiving fresh when(…) wiring at the top of each @Test. Because the field VALUE is the bean, there is no scope proxying — @Singleton by default; the test asserting .isSameAs(WELCOME_GREETING) proves it.

@ConfigBean — typed config facade

A @ConfigBean-annotated class is an @ApplicationScoped CDI bean (the annotation is a stereotype that contributes the scope). @Inject ConfigResolver and expose one public method per config key with parsing + default.

listing 05 · config-beanlistings/05-config-bean/
// src/main/java/example/configbean/AppConfig.java
@ConfigBean
public class AppConfig {

    @Inject
    ConfigResolver resolver;

    public String greeting() {
        return resolver.resolve("app.greeting").orElse("hi");
    }

    public int retries() {
        return resolver.resolve("app.retries").map(Integer::parseInt).orElse(3);
    }
}

// src/main/resources/META-INF/microprofile-config.properties
app.greeting = hello from MicroProfile Config
app.retries  = 5

2. detailed

2.1 @EnableTestBeans

@EnableTestBeans is the one annotation that turns jawelte on for a JUnit 5 test class. It carries two options:

limitToTestBeans (default false)

When true, CDI bean discovery is restricted to classes named in a @TestBean declaration on the test class (or one of its superclasses, directly or via meta-annotation) plus framework internals. Auto-mocking is disabled. Production beans not whitelisted are vetoed at discovery time.

listing 06 · limit-to-test-beanslistings/06-limit-to-test-beans/
@EnableTestBeans(limitToTestBeans = true)
@TestBean(bean = StubEmailService.class)
class LimitToTestBeansTest {

    @Inject
    BeanManager beanManager;

    @Inject
    EmailService emailService;

    @Test
    void onlyDeclaredTestBeansAreInTheContainer() {
        assertThat(emailService.send("alice@example.com")).isEqualTo("stub:alice@example.com");
        // Production @ApplicationScoped beans not in any @TestBean were vetoed at discovery.
        assertThat(beanManager.getBeans(SmtpEmailService.class)).isEmpty();
        assertThat(beanManager.getBeans(AuditService.class)).isEmpty();
    }
}

manageContainer (default true)

When true, jawelte calls TestBeanContainerPort.beforeAll and afterAll to boot and shut down the CDI container. When false, those calls are skipped — the test owns the container lifecycle (e.g., via SeContainerInitializer). The per-method scope activation and field injection still happen.

listing 07 · external-containerlistings/07-external-container/
@EnableTestBeans(manageContainer = false)
class ExternalContainerTest {

    private static SeContainer container;

    @BeforeAll
    static void bootCdi() {
        container = SeContainerInitializer.newInstance().initialize();
    }

    @AfterAll
    static void shutdownCdi() {
        container.close();
    }

    @Inject
    Counter counter;

    @Inject
    BeanManager beanManager;

    @Test
    void requestScopeStillActive() {
        assertThat(beanManager.getContext(RequestScoped.class).isActive()).isTrue();
        assertThat(counter.increment()).isEqualTo(1);
    }
}

2.2 @TestBean modes

@TestBean declares per-test-class bean replacements. Three modes, mutually exclusive within a single declaration:

  • @TestBean(bean = X.class) — activate the @Alternative class X for this test class. See listing 03 in the quick-start.
  • @TestBean(beanProducer = P.class) — activate the producer-method @Alternative class P. The @Produces methods live on P; @TestBean points at the producer class as a whole. Listing 08 below.
  • @TestBean on a static field — the field VALUE becomes the bean instance, scope @Singleton, qualifiers from the field. See listing 04.

@TestBean's @Target is {TYPE, ANNOTATION_TYPE, FIELD} — it cannot be placed directly on a @Produces method; the producer-method route always goes through a producer-class indirection (the beanProducer= form above).

@TestBean is @Repeatable via the @TestBeans container annotation. Multiple @TestBeans on a class are aggregated automatically; no need to write the container by hand.

beanProducer mode

listing 08 · test-bean-producerlistings/08-test-bean-producer/
// src/test/java/example/producer/FixedClockProducer.java
@Dependent
@Alternative
public class FixedClockProducer {

    static final Instant FIXED_INSTANT = Instant.parse("2026-05-20T12:00:00Z");

    @Produces
    public Clock fixedClock() {
        return () -> FIXED_INSTANT;
    }
}

// src/test/java/example/producer/ClockTest.java
@EnableTestBeans
@TestBean(beanProducer = FixedClockProducer.class)
class ClockTest {

    @Inject
    Clock clock;

    @Test
    void yieldsTheFixedInstant() {
        assertThat(clock.now()).isEqualTo(FixedClockProducer.FIXED_INSTANT);
    }
}

@TestBean on a meta-annotation

Wrap a @TestBean in your own annotation and apply that annotation across many test classes. jawelte's scanner walks the annotation graph recursively (cycle-safe; java. / jakarta. packages are skipped), so the trick composes: a meta-annotation can itself carry other meta-annotations and they ALL contribute their @TestBeans to the test class.

listing 09 · test-bean-meta-annotationlistings/09-test-bean-meta-annotation/
// src/test/java/example/meta/WithStubEmail.java — one small reusable unit
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@TestBean(bean = StubEmailService.class)
public @interface WithStubEmail {
}

// src/test/java/example/meta/WithStubClock.java — another small reusable unit
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@TestBean(bean = StubClock.class)
public @interface WithStubClock {
}

// src/test/java/example/meta/WithFullStubBackend.java — composes the two
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@WithStubEmail
@WithStubClock
public @interface WithFullStubBackend {
}

// src/test/java/example/meta/FullStubBackendTest.java
@EnableTestBeans
@WithFullStubBackend      // one label, both stubs activated
class FullStubBackendTest {

    @Inject
    EmailService emailService;

    @Inject
    Clock clock;

    @Test
    void aggregatingMetaAnnotationActivatesBothStubs() {
        assertThat(emailService.send("alice@example.com")).isEqualTo("stub:alice@example.com");
        assertThat(clock.now()).isEqualTo(StubClock.PINNED);
    }
}

Pattern for larger test suites: keep one tiny meta-annotation per fixture (one stub each, one job each), then assemble them into named scenarios — @WithFullStubBackend here, but realistic suites grow concepts like @WithSmtpAndAuditOff, @WithFrozenClockUtc, @WithReadOnlyDatabase. The test classes apply exactly one such label and stay free of @TestBean wiring noise.

2.3 @ConfigBean

@ConfigBean is a CDI @Stereotype that meta-applies @ApplicationScoped. A class annotated @ConfigBean is therefore a regular CDI bean with application scope; the user does not declare @ApplicationScoped explicitly.

The intended usage pattern is to @Inject the ConfigResolver port into a @ConfigBean class and expose one public method per config key. Each method delegates the raw lookup to the resolver and is responsible for parsing / converting the String value and supplying a meaningful default. See listing 05 in the quick-start for the canonical shape.

The annotation defines no interceptors and no additional behavior beyond the stereotype's scope contribution. It also serves as a discovery marker so that, for example, limitToTestBeans can identify config beans.

2.4 events

jawelte fires three CDI events at well-defined lifecycle points. Module code observes them with plain @Observes.

ContainerStarted

Fired by the TestBeanContainerPort implementation inside its beforeAll, after the CDI container is ready but before any TestModuleLifecyclePort.beforeAll runs. Useful for module-style one-time setup that needs CDI but must complete before lifecycle ports run.

listing 12 · container-startedlistings/12-container-started/
@ApplicationScoped
public class StartupRecorder {
    public static final AtomicReference<Class<?>> OBSERVED_TEST_CLASS = new AtomicReference<>();

    public void onContainerStarted(@Observes ContainerStarted event) {
        OBSERVED_TEST_CLASS.set(event.getTestClass());
    }
}

BeforeScopeStarted

Fired before a per-method scope (e.g., @RequestScoped) is activated. Observers may call event.veto() to keep the scope inactive for that test method.

listing 11 · before-scope-vetolistings/11-before-scope-veto/
@ApplicationScoped
public class RequestScopeVetoer {
    public void onBeforeScopeStarted(@Observes BeforeScopeStarted event) {
        if (event.getScope() == RequestScoped.class) {
            event.veto();
        }
    }
}

AfterTestTransaction

Defined in core as a contract; fired only when a transaction-managing module is on the classpath. See that module's documentation for when it fires and what the committed flag means in that context.

2.5 lifecycle ordering

jawelte invokes lifecycle callbacks in a specific order across the active ports:

  • beforeAll — TestBeanContainerPort.beforeAll first; then each TestModuleLifecyclePort.beforeAll in ascending @Priority order. Ports without @Priority get an effective priority of Integer.MAX_VALUE (run last).
  • postProcessTestInstance — TestBeanContainerPort.postProcessTestInstance once after the test class constructor.
  • beforeEach — TestBeanContainerPort.beforeEach first; then each TestModuleLifecyclePort.beforeEach in ascending priority.
  • afterEach — each TestModuleLifecyclePort.afterEach in reverse (LIFO) order; then TestBeanContainerPort.afterEach.
  • afterAll — each TestModuleLifecyclePort.afterAll in reverse order; then TestBeanContainerPort.afterAll if manageContainer=true.

Cleanup guarantee: only ports that completed their before* receive the matching after*. If before* on some port threw, ports earlier in the chain still get their after*; the thrown exception is the primary and the rest are attached via Throwable.addSuppressed.

3. spi / port reference

core defines the entire jawelte port surface. Each port is either single-impl (exactly one implementation must be on the classpath; multiple-impl raises an error) or multi-impl (any number; the active ServicePriorityResolver orders them). Some are discovered via ServiceLoader; ConfigResolver is a CDI bean.

3.1 TestContext

TestContext is the per-test-class facade every non-JUnit jawelte port receives — every method on every port below takes a TestContext argument. It carries:

  • getTestClass() — the JUnit test class.
  • bindMetadata(Class<T> key, T value) / getMetadata(Class<T>) / unbindMetadata(Class<T>) — typed per-test-class state. The Class<T> token is both the key and the type witness. Port implementations that need state across their own callbacks bind it here rather than holding instance fields.
  • Two static helpers: TestContext.get() (the active context on the calling thread, usable only inside the bootstrap window of core/impl's delegating extension); TestContext.loadService(Class) (the project-wide canonical priority-resolved SPI lookup).
listing 10 · test-context-metadatalistings/10-test-context-metadata/
// src/test/java/example/metadata/BootstrapTimestampLifecyclePort.java
public class BootstrapTimestampLifecyclePort implements TestModuleLifecyclePort {

    public static final AtomicReference<StartupRecord> BOUND_IN_BEFORE_ALL = new AtomicReference<>();
    public static final AtomicReference<StartupRecord> SEEN_IN_BEFORE_EACH = new AtomicReference<>();

    @Override
    public void beforeAll(TestContext testContext) {
        StartupRecord record = new StartupRecord(System.currentTimeMillis());
        testContext.bindMetadata(StartupRecord.class, record);
        BOUND_IN_BEFORE_ALL.set(record);
    }

    @Override
    public void beforeEach(TestContext testContext) {
        SEEN_IN_BEFORE_EACH.set(testContext.getMetadata(StartupRecord.class).orElse(null));
    }
}

3.2 TestBeanContainerPort

Single-impl, ServiceLoader. The CDI runtime adapter. The delegating JUnit extension forwards every test-lifecycle callback to this port. cdi-module ships the OWB/Weld SE adapter (CdiTestBeanContainer). The user does not usually implement this port.

3.3 TestModuleLifecyclePort

Multi-impl, ServiceLoader. The way feature modules participate in the test lifecycle. All methods default to no-ops; an implementation overrides only the callbacks it cares about. Sorted by @Priority ascending for before*, reverse for after*.

listing 13 · lifecycle-portlistings/13-lifecycle-port/
@Priority(10)
public class EarlyLifecyclePort implements TestModuleLifecyclePort {

    @Override
    public void beforeAll(TestContext testContext) {
        LifecycleLog.EVENTS.add("early.beforeAll");
    }
}

@Priority(20)
public class LateLifecyclePort implements TestModuleLifecyclePort {

    @Override
    public void beforeAll(TestContext testContext) {
        LifecycleLog.EVENTS.add("late.beforeAll");
    }
}

3.4 TestInstanceFactoryPort

Single-impl (optional), ServiceLoader. Produces the test-instance JUnit will use. When present, JUnit receives the bean instance the implementation produces; when absent, jawelte falls back to testClass.getDeclaredConstructor().newInstance(). cdi-module ships an impl that does CDI.current().select(testClass).get() so test classes participate in CDI-managed lifecycle (private fields, package-private classes, JUnit's PER_METHOD all keep working).

3.5 BeanScopeMapper + BeanScopeMapperPort

Two related ports for declarative CDI scope rewriting at ProcessAnnotatedType time.

  • BeanScopeMapper — multi-impl, ServiceLoader. Each provider names a trigger annotation (trigger()) and a target scope (targetScope()). The fixed CDI extension in core/impl walks the providers for every type the CDI runtime delivers and, on the first whose trigger is directly present, removes the type's directly-declared CDI scopes and adds the target.
  • BeanScopeMapperPort — single-impl, loaded via TestContext.loadService. The driven port that the fixed CDI extension delegates to. Default impl iterates the BeanScopeMapper providers; replace this port to install an entirely custom remap policy.
listing 14 · bean-scope-mapperlistings/14-bean-scope-mapper/
public class RequestToApplicationScoped implements BeanScopeMapper {

    @Override
    public Class<? extends Annotation> trigger() {
        return RequestScoped.class;
    }

    @Override
    public Class<? extends Annotation> targetScope() {
        return ApplicationScoped.class;
    }
}

3.6 ConfigResolver

Single active impl, CDI bean (NOT ServiceLoader). Resolves config keys to their raw String values. @ConfigBean classes inject it and call resolve(dotKey). The default impl in core/impl looks up via MicroProfile Config with the documented two-step fallback (dotKey first, then the underscore variant if and only if dotKey contained at least one .).

Users override with an @Alternative @Priority(...) CDI bean — CDI 4's globally-enabled alternative rule selects the highest-priority alternative over the framework default (which carries no @Alternative).

listing 15 · config-resolverlistings/15-config-resolver/
@ApplicationScoped
@Alternative
@Priority(100)
public class FixedConfigResolver implements ConfigResolver {

    private static final Map<String, String> FIXED_VALUES = Map.of(
            "app.greeting", "hello-from-test-resolver");

    @Override
    public Optional<String> resolve(String dotKey) {
        return Optional.ofNullable(FIXED_VALUES.get(dotKey));
    }

    @Override
    public Iterable<String> resolveKeys() {
        return FIXED_VALUES.keySet();
    }

    @Override
    public List<String> resolveAliasKeysFor(String logicalKey) {
        return List.of();
    }
}

3.7 ConfigKeyAliasProvider

Multi-impl, ServiceLoader. The way a non-owning module contributes module-specific MP Config keys to a logical configuration key owned by another module. The owning module reads its own key directly and merges the contributor keys this port returns into the final value. The concrete cross-module wiring lives in the docs of the contributing modules.

3.8 ServicePriorityResolver

Single active impl, bootstrap via MP Config. The project-wide canonical mechanism for ordering provider lists. Replace it via the MP Config bootstrap key org.os890.jawelte.core.api.port.ServicePriorityResolver — value is the FQCN of an impl class with a public no-arg constructor. Every TestContext.loadService(Class) SPI selection routes through the active resolver.

listing 16 · priority-resolverlistings/16-priority-resolver/
public class ReversePriorityResolver implements ServicePriorityResolver {

    @Override
    public <T> List<T> sort(List<T> providers) {
        List<T> copy = new ArrayList<>(providers);
        copy.sort(Comparator.comparingInt(ReversePriorityResolver::priorityOf).reversed());
        return copy;
    }

    private static int priorityOf(Object provider) {
        Priority priority = provider.getClass().getAnnotation(Priority.class);
        return priority == null ? Integer.MIN_VALUE : priority.value();
    }
}

// surefire argLine: -Dorg.os890.jawelte.core.api.port.ServicePriorityResolver=...ReversePriorityResolver

Caveat. core's own DelegatingJUnitExtension sorts TestModuleLifecyclePort via a hardcoded PriorityComparator rather than the resolver. The resolver applies to ports loaded through TestContext.loadService(...) (cdi-module's MockFactory / WhitelistFilter, content-diff's matchers, …) — that's where swapping the resolver shifts the active provider.

3.9 TestBeansExtension

Single-impl, ServiceLoader. You almost never touch this. The bootstrap SPI EnableTestBeans.Proxy loads to delegate every JUnit callback to. Implemented once by core/impl (DelegatingJUnitExtension); shipping a second implementation breaks bootstrap (zero / multiple impls raise IllegalStateException on first callback). Listed here for completeness — replace it only to fork the JUnit-side glue itself.

3.10 config bootstrap keys

core reads exactly two MicroProfile Config keys; both name the FQCN of a port impl with a public no-arg constructor. Both accept the underscore variant as a fallback (per MP Config's environment-variable mapping rule).

KeyDefaultSelects
org.os890.jawelte.core.api.port.TestContext org.os890.jawelte.core.impl.adapter.context.TestContextImpl The accessor returned by TestContext.get() — section 3.1.
