core is jawelte's contract layer. It turns JUnit 5 lifecycle hooks into your CDI container's lifecycle, defines the annotations test authors actually use (@EnableTestBeans, @TestBean, @ConfigBean), and ships the ports every other module plugs into. core does not ship a container. Pair it with cdi-module (the default adapter for OpenWebBeans / Weld SE) — every example on this page assumes that pairing.

Every code block on this page links to a runnable sample under listings/. Each sample is a stand-alone Maven project — copy a folder out of the repository and run mvn test on it without any other setup.

1. quick-start

1.1 purpose

core exposes a JUnit 5 extension (@EnableTestBeans) that boots a CDI container around your test class, populates @Inject fields on the test instance, activates the request scope around each test method, and tears everything down afterwards. The test author writes plain JUnit; jawelte does the wiring.

On top of the lifecycle, core defines three annotations the test author touches directly:

  • @EnableTestBeans — switches the extension on for a class; carries two options (limitToTestBeans, manageContainer) covered in section 2.1.
  • @TestBean — picks per-test-class bean replacements (alternative class, producer-method class, or a pre-built value via a static field). Covered in 2.2.
  • @ConfigBean — declares a typed configuration facade backed by jawelte's ConfigResolver. Covered in section 4 at the back of the page (it's a usage pattern on top of CDI + ConfigResolver, not a core mechanism).

Two more layers sit underneath the annotations and matter once you're past hello-world:

  • Events — ContainerStarted, BeforeScopeStarted, AfterTestTransaction — fire at well-defined points and let module code react to the lifecycle.
  • Ports — the SPI surface every adapter plugs into (TestBeanContainerPort, TestModuleLifecyclePort, ConfigResolver, BeanScopeMapper, …). Section 3 walks them.

1.2 hello-world

A plain @ApplicationScoped bean in src/main, a JUnit test in src/test annotated @EnableTestBeans, one @Inject field, one assertion. That's the whole shape.

listing core · hello-worldlistings/core/01-hello-world/
// src/main/java/example/hello/HelloService.java
@ApplicationScoped
public class HelloService {
    public String greet(String name) {
        return "hello, " + name + "!";
    }
}

// src/test/java/example/hello/HelloServiceTest.java
@EnableTestBeans
class HelloServiceTest {

    @Inject
    HelloService helloService;

    @Test
    void greetsByName() {
        assertThat(helloService.greet("jawelte")).isEqualTo("hello, jawelte!");
    }
}

Run mvn test from inside the listing folder; one test passes in under a second. The CDI container booted by jawelte discovered HelloService, injected it into the test instance, ran the test method inside an active request scope, and shut down.

1.3 common use-cases

auto-mocked dependency

Production code @Injects a collaborator with no implementation on the classpath. jawelte's default MockFactory (a Mockito wrapper) supplies a mock; the test stubs it with plain Mockito.

listing core · auto-mocklistings/core/02-auto-mock/
// src/main/java/example/automock/Translator.java
public interface Translator { String translate(String value); }

// src/main/java/example/automock/Greeter.java
@ApplicationScoped
public class Greeter {

    @Inject
    Translator translator;

    public String greet(String name) {
        return "hello, " + translator.translate(name) + "!";
    }
}

// src/test/java/example/automock/GreeterTest.java
@EnableTestBeans
class GreeterTest {

    @Inject
    Greeter greeter;

    @Inject
    Translator translator;  // SAME auto-mock Greeter sees

    @Test
    void unsatisfiedDependencyIsAutoMocked() {
        when(translator.translate("jawelte")).thenReturn("JAWELTE");
        assertThat(greeter.greet("jawelte")).isEqualTo("hello, JAWELTE!");
    }
}

lifecycle & sharing of auto-mocks

Auto-mocks are @RequestScoped by default. jawelte registers exactly one synthetic bean per (target-type, qualifier-set) shape — every injection point matching that shape resolves to the same mock instance for the duration of the current test method. So Greeter.translator (held by the application-scoped production bean) and GreeterTest.translator (the test class field) point at the identical mock; when(translator…) on the test side stubs exactly what greeter.greet(…) reads on the production side.

The request scope is freshly activated in beforeEach and torn down in afterEach, so each test method gets its own fresh mock. Stubs you set up in one method never bleed into the next — Mockito state resets implicitly with the scope. Add a second @Test method that doesn't call when(…) and translator.translate(…) returns Mockito's default null again.

The default scope is configurable; the exact MP Config key and what each module rebinds it to is covered in the cdi-module / scope-module documentation. JDK types (String, primitives, the final classes mocking can't subclass…) are auto-mocked at @Dependent scope so each injection point gets its own instance — the framework can't put a normal-scope proxy on a final class.

The compatibility footnote on Mockito + Byte Buddy + JDK 25 (why the listings pin mockito-core 5.23.0) lives in §1.4 below — skip it on first read.

@TestBean — pick an alternative

A test-only @Alternative class wins over the production impl when its class is named in @TestBean(bean=…) on the test class.

listing core · test-bean-alternativelistings/core/03-test-bean-alternative/
// src/test/java/example/alternative/StubEmailService.java
@Alternative
@ApplicationScoped
public class StubEmailService implements EmailService {

    @Override
    public String send(String to) {
        return "stub:" + to;
    }
}

// src/test/java/example/alternative/EmailServiceTest.java
@EnableTestBeans
@TestBean(bean = StubEmailService.class)
class EmailServiceTest {

    @Inject
    EmailService emailService;

    @Test
    void stubAlternativeWins() {
        assertThat(emailService.send("alice@example.com")).isEqualTo("stub:alice@example.com");
    }
}

@TestBean — pre-built value on a static field

Put @TestBean on a static final field whose initialiser yields the bean instance. No @Alternative, no producer — the field value IS the bean. Idiomatic for "register this exact object as the bean". The two static fields below show the two most common shapes side by side: a literal value (new Greeting(…)) and a Mockito mock (Mockito.mock(Clock.class)) wired in via the same static-field recipe.

Where the injection point lives is the key: a production-shaped @ApplicationScoped service (WelcomeService, in src/main) @Injects Greeting and Clock — it has no idea those values came from a test class's static fields. The test exercises the service, and the service receives the static-field values because they're registered as CDI beans. Putting the @Inject on the test class itself would still work, but blurs the lesson — readers might think it's just a static-field reference, not a container-managed injection.

listing core · test-bean-static-fieldlistings/core/04-test-bean-static-field/
// src/main/java/example/staticfield/Greeting.java
public record Greeting(String text) {
}

// src/main/java/example/staticfield/Clock.java
@FunctionalInterface
public interface Clock {
    Instant now();
}

// src/main/java/example/staticfield/WelcomeService.java   (production-shaped consumer)
@ApplicationScoped
public class WelcomeService {

    @Inject
    Greeting greeting;

    @Inject
    Clock clock;

    public String compose() {
        return greeting.text() + " @ " + clock.now();
    }
}

// src/test/java/example/staticfield/GreetingTest.java
@EnableTestBeans
class GreetingTest {

    @TestBean
    public static final Greeting WELCOME_GREETING = new Greeting("hello-from-static-field");

    @TestBean
    public static final Clock CLOCK = mock(Clock.class);

    // Injection point lives in a production-shaped bean (above), not on the test class.
    @Inject
    WelcomeService welcomeService;

    @Test
    void serviceReceivesTheStaticFieldsViaCdi() {
        Instant pinned = Instant.parse("2026-05-20T12:00:00Z");
        when(CLOCK.now()).thenReturn(pinned);

        assertThat(welcomeService.compose())
                .as("WelcomeService composed its String from the @TestBean Greeting + the stubbed @TestBean Clock")
                .isEqualTo("hello-from-static-field @ 2026-05-20T12:00:00Z");
    }

    // Secondary identity check — the field value IS the bean instance, no copy / no proxy.
    @Inject
    Greeting greetingDirect;

    @Test
    void staticFieldValueIsTheSameInstanceTheContainerHandsOut() {
        assertThat(greetingDirect).isSameAs(WELCOME_GREETING);
    }
}

Both static-field declarations register their respective values once at class-load time — WELCOME_GREETING stays the same literal record across the whole test class; CLOCK stays the same Mockito mock instance, with stubs reset between methods by Mockito's @Singleton-scoped instance receiving fresh when(…) wiring at the top of each @Test. Because the field VALUE is the bean, there is no scope proxying — @Singleton by default; the second test's .isSameAs(WELCOME_GREETING) proves it.

@TestBean — replace a qualified injection point (advanced)

When the production injection point carries a CDI qualifier (@Inject @FastCache Cache, @Inject @Premium PaymentService, …), the alternative must declare the same qualifier on its own class. @TestBean does not name qualifiers explicitly — the qualifier travels with the alternative class declaration. This is a sub-mode of the plain @Alternative pattern above; skip on a first read unless you're already comfortable with CDI qualifiers.

listing core · test-bean-qualifiedlistings/core/17-test-bean-qualified/
// src/main/java/example/qualified/FastCache.java
@Qualifier
@Retention(RUNTIME)
@Target({FIELD, METHOD, PARAMETER, TYPE})
public @interface FastCache {
}

// src/main/java/example/qualified/RedisCache.java   (production impl)
@FastCache
@ApplicationScoped
public class RedisCache implements Cache {
    @Override public String get(String key) { return "redis:" + key; }
}

// src/test/java/example/qualified/InMemoryFastCache.java   (test alternative, same qualifier)
@Alternative
@FastCache
@ApplicationScoped
public class InMemoryFastCache implements Cache {
    @Override public String get(String key) { return "in-memory:" + key; }
}

// src/test/java/example/qualified/FastCacheTest.java
@EnableTestBeans
@TestBean(bean = InMemoryFastCache.class)
class FastCacheTest {

    @Inject
    @FastCache
    Cache fastCache;

    @Test
    void qualifiedAlternativeReplacesQualifiedInjection() {
        assertThat(fastCache.get("k")).isEqualTo("in-memory:k");
    }
}

A second injection point at @Inject Cache (unqualified, or with a different qualifier) is unaffected — the alternative only beats out beans whose qualifier set matches.

ⓘMockito version on JDK 25

The listings pin mockito-core 5.23.0 deliberately. Mockito's default inline mock maker rewrites bytecode at runtime via Byte Buddy; older Mockito releases (e.g. 5.14.2) bundled Byte Buddy 1.15.4, which only knows class files up to Java 24 (major version 68). Under JDK 25 (major 69), Mockito.mock(...) throws

java.lang.IllegalArgumentException: Java 25 (69) is not supported by the
current version of Byte Buddy which officially supports Java 24 (68)

jawelte's MockitoMockFactory catches the exception and returns null, the auto-mock synthetic bean is never registered, and @Inject Translator fails with UnsatisfiedResolutionException at container boot. Mockito 5.23.0 ships Byte Buddy 1.17.7, which understands Java 26's class file (major 70) and therefore Java 25 too — picking that version is enough; no mockito-extensions/org.mockito.plugins.MockMaker override and no -Dnet.bytebuddy.experimental=true JVM flag.

If you have to keep an older Mockito on the classpath (transitive dep clash, internal artifact-policy, …), the same fix can be applied by overriding only Byte Buddy: pin net.bytebuddy:byte-buddy + net.bytebuddy:byte-buddy-agent to 1.17.7 (or newer) in your <dependencyManagement>. The mock-maker-subclass config file route is the last-resort fallback when neither version bump is possible.

2. detailed

2.1 @EnableTestBeans

@EnableTestBeans is the one annotation that turns jawelte on for a JUnit 5 test class. It carries two options:

limitToTestBeans (default false)

When true, CDI bean discovery is restricted to classes named in a @TestBean declaration on the test class (or one of its superclasses, directly or via meta-annotation) plus framework internals. Auto-mocking is disabled. Production beans not whitelisted are vetoed at discovery time.

listing core · limit-to-test-beanslistings/core/06-limit-to-test-beans/
// src/main/java/example/strict/EmailService.java  — the interface the production code depends on
public interface EmailService { String send(String to); }

// src/main/java/example/strict/SmtpEmailService.java  — real production impl (vetoed under limitToTestBeans=true)
@ApplicationScoped
public class SmtpEmailService implements EmailService { ... }

// src/main/java/example/strict/AuditService.java  — unrelated @ApplicationScoped bean (also vetoed)
@ApplicationScoped
public class AuditService { ... }

// src/test/java/example/strict/StubEmailService.java  — @Alternative the test names via @TestBean
@Alternative @ApplicationScoped
public class StubEmailService implements EmailService {
    @Override public String send(String to) { return "stub:" + to; }
}

// src/test/java/example/strict/LimitToTestBeansTest.java
@EnableTestBeans(limitToTestBeans = true)
@TestBean(bean = StubEmailService.class)
class LimitToTestBeansTest {

    @Inject
    BeanManager beanManager;

    @Inject
    EmailService emailService;

    @Test
    void onlyDeclaredBeansSurvive() {
        assertThat(emailService.send("alice@example.com")).isEqualTo("stub:alice@example.com");
        // Production @ApplicationScoped beans not in any @TestBean were vetoed at discovery.
        assertThat(beanManager.getBeans(SmtpEmailService.class)).isEmpty();
        assertThat(beanManager.getBeans(AuditService.class)).isEmpty();
    }
}

manageContainer (default true)

Controls whether jawelte boots and shuts down the CDI container. This flag has no effect on JUnit's own lifecycle — your @BeforeAll / @AfterAll methods on the test class are always called by JUnit, regardless of the flag.

With manageContainer = true (default) jawelte's DelegatingJUnitExtension calls TestBeanContainerPort.beforeAll(TestContext) from inside JUnit's beforeAll phase (the call that boots the CDI container) and TestBeanContainerPort.afterAll(TestContext) from inside afterAll (the call that shuts it down). See §3.2 TestBeanContainerPort for the port itself.

With manageContainer = false jawelte skips just those two port invocations — the boot and the shutdown. You're expected to boot the container yourself from a @BeforeAll method (typically via SeContainerInitializer) and close it from @AfterAll; the listing below shows the exact shape. Everything else jawelte does still runs: TestModuleLifecyclePort.beforeAll / afterAll still fire on every registered lifecycle port, and per-method behaviour is unchanged — postProcessTestInstance (field injection on the test instance), beforeEach (scope activation), and afterEach (scope deactivation) all happen as before.

listing core · external-containerlistings/core/07-external-container/
// src/main/java/example/external/Counter.java  — ordinary @ApplicationScoped bean
@ApplicationScoped
public class Counter {
    private int count;
    public int increment() { return ++count; }
    public int value() { return count; }
}

// src/test/java/example/external/ExternalContainerTest.java
@EnableTestBeans(manageContainer = false)
class ExternalContainerTest {

    private static SeContainer container;

    @BeforeAll
    static void bootCdi() {
        container = SeContainerInitializer.newInstance().initialize();
    }

    @AfterAll
    static void shutdownCdi() {
        if (container != null) {
            container.close();
        }
    }

    @Inject
    Counter counter;

    @Inject
    BeanManager beanManager;

    @Test
    void requestScopeIsActive() {
        assertThat(beanManager.getContext(RequestScoped.class).isActive()).isTrue();
        assertThat(counter.increment()).isEqualTo(1);
        assertThat(counter.value()).isEqualTo(1);
    }
}

2.2 @TestBean modes

@TestBean declares per-test-class bean replacements. Three modes, mutually exclusive within a single declaration:

  • @TestBean(bean = X.class) — activate the @Alternative class X for this test class. See listing 03 in the quick-start.
  • @TestBean(beanProducer = P.class) — activate the producer-method @Alternative class P. The @Produces methods live on P; @TestBean points at the producer class as a whole. Listing 08 below.
  • @TestBean on a static field — the field VALUE becomes the bean instance, scope @Singleton, qualifiers from the field. See listing 04.

@TestBean's @Target is {TYPE, ANNOTATION_TYPE, FIELD} — it cannot be placed directly on a @Produces method; the producer-method route always goes through a producer-class indirection (the beanProducer= form above).

@TestBean is @Repeatable via the @TestBeans container annotation. Multiple @TestBeans on a class are aggregated automatically; no need to write the container by hand.

beanProducer mode

listing core · test-bean-producerlistings/core/08-test-bean-producer/
// src/test/java/example/producer/FixedClockProducer.java
@Dependent
@Alternative
public class FixedClockProducer {

    static final Instant FIXED_INSTANT = Instant.parse("2026-05-20T12:00:00Z");

    @Produces
    public Clock fixedClock() {
        return () -> FIXED_INSTANT;
    }
}

// src/test/java/example/producer/ClockTest.java
@EnableTestBeans
@TestBean(beanProducer = FixedClockProducer.class)
class ClockTest {

    @Inject
    Clock clock;

    @Test
    void yieldsTheFixedInstant() {
        assertThat(clock.now()).isEqualTo(FixedClockProducer.FIXED_INSTANT);
    }
}

@TestBean on a meta-annotation

Wrap a @TestBean in your own annotation and apply that annotation across many test classes. jawelte's scanner walks the annotation graph recursively (cycle-safe; java. / jakarta. packages are skipped), so the trick composes: a meta-annotation can itself carry other meta-annotations and they ALL contribute their @TestBeans to the test class.

listing core · test-bean-meta-annotationlistings/core/09-test-bean-meta-annotation/
// src/test/java/example/meta/WithStubEmail.java — one small reusable unit
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@TestBean(bean = StubEmailService.class)
public @interface WithStubEmail {
}

// src/test/java/example/meta/WithStubClock.java — another small reusable unit
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@TestBean(bean = StubClock.class)
public @interface WithStubClock {
}

// src/test/java/example/meta/WithFullStubBackend.java — composes the two
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@WithStubEmail
@WithStubClock
public @interface WithFullStubBackend {
}

// src/test/java/example/meta/FullStubBackendTest.java
@EnableTestBeans
@WithFullStubBackend      // one label, both stubs activated
class FullStubBackendTest {

    @Inject
    EmailService emailService;

    @Inject
    Clock clock;

    @Test
    void bothStubsActivated() {
        assertThat(emailService.send("alice@example.com")).isEqualTo("stub:alice@example.com");
        assertThat(clock.now()).isEqualTo(StubClock.PINNED);
    }
}

Pattern for larger test suites: keep one tiny meta-annotation per fixture (one stub each, one job each), then assemble them into named scenarios — @WithFullStubBackend here, but realistic suites grow concepts like @WithSmtpAndAuditOff, @WithFrozenClockUtc, @WithReadOnlyDatabase. The test classes apply exactly one such label and stay free of @TestBean wiring noise.

2.3 events

jawelte fires three CDI events at well-defined lifecycle points. Module code observes them with plain @Observes.

ContainerStarted

Fired by the TestBeanContainerPort implementation inside its beforeAll, after the CDI container is ready but before any TestModuleLifecyclePort.beforeAll runs. Useful for module-style one-time setup that needs CDI but must complete before lifecycle ports run.

listing core · container-startedlistings/core/12-container-started/
@ApplicationScoped
public class StartupRecorder {
    public static final AtomicReference<Class<?>> OBSERVED_TEST_CLASS = new AtomicReference<>();

    public void onContainerStarted(@Observes ContainerStarted event) {
        OBSERVED_TEST_CLASS.set(event.getTestClass());
    }
}

BeforeScopeStarted

Fired before a per-method scope (e.g., @RequestScoped) is activated. The most common reaction is to observe and log; event.veto() is also available and keeps the scope inactive for the test method, but veto is rare in practice.

listing core · before-scope-observerlistings/core/11-before-scope-observer/
@ApplicationScoped
public class ScopeStartLogger {

    private static final Logger LOG = Logger.getLogger(ScopeStartLogger.class.getName());

    public static final List<Class<? extends Annotation>> OBSERVED_SCOPES = new CopyOnWriteArrayList<>();

    public void onBeforeScopeStarted(@Observes BeforeScopeStarted event) {
        LOG.info("scope about to start: " + event.getScope().getSimpleName());
        OBSERVED_SCOPES.add(event.getScope());
    }
}

AfterTestTransaction

Defined in core as a contract; fired only when a transaction-managing module is on the classpath. See that module's documentation for when it fires and what the committed flag means in that context. The observer shape is the same as for the events above:

@ApplicationScoped
public class TxAuditor {
    public void onAfterTx(@Observes AfterTestTransaction event) {
        // event.isCommitted() vs rollback; event.getTestClass() / event.getTestMethod() available too.
    }
}

See jpa-module · §2.5 transaction events for the firing rules in the JPA case (paired with TransactionStarted) and jta-module for the JTA variant.

2.4 lifecycle ordering

jawelte invokes lifecycle callbacks in a specific order across the active ports:

  • beforeAll — TestBeanContainerPort.beforeAll first; then each TestModuleLifecyclePort.beforeAll in ascending @Priority order. Ports without @Priority get an effective priority of Integer.MAX_VALUE (run last).
  • postProcessTestInstance — TestBeanContainerPort.postProcessTestInstance once after the test class constructor.
  • beforeEach — TestBeanContainerPort.beforeEach first; then each TestModuleLifecyclePort.beforeEach in ascending priority.
  • afterEach — each TestModuleLifecyclePort.afterEach in reverse (LIFO) order; then TestBeanContainerPort.afterEach.
  • afterAll — each TestModuleLifecyclePort.afterAll in reverse order; then TestBeanContainerPort.afterAll if manageContainer=true.

Cleanup guarantee: only ports that completed their before* receive the matching after*. If before* on some port threw, ports earlier in the chain still get their after*; the thrown exception is the primary and the rest are attached via Throwable.addSuppressed.

3. spi / port reference

core defines the entire jawelte port surface. Each port is either single-impl (exactly one implementation must be on the classpath; multiple-impl raises an error) or multi-impl (any number; the active ServicePriorityResolver orders them). Some are discovered via ServiceLoader; ConfigResolver is a CDI bean.

3.1 TestContext

TestContext is the per-test-class facade every non-JUnit jawelte port receives — every method on every port below takes a TestContext argument. It carries:

  • getTestClass() — the JUnit test class.
  • bindMetadata(Class<T> key, T value) / getMetadata(Class<T>) / unbindMetadata(Class<T>) — typed per-test-class state. The Class<T> token is both the key and the type witness. Port implementations that need state across their own callbacks bind it here rather than holding instance fields.
  • Two static helpers: TestContext.get() (the active context on the calling thread, usable only inside the bootstrap window of core/impl's delegating extension); TestContext.loadService(Class) (the project-wide canonical priority-resolved SPI lookup).
listing core · test-context-metadatalistings/core/10-test-context-metadata/
// src/test/java/example/metadata/BootstrapTimestampLifecyclePort.java
public class BootstrapTimestampLifecyclePort implements TestModuleLifecyclePort {

    public static final AtomicReference<StartupRecord> BOUND_IN_BEFORE_ALL = new AtomicReference<>();
    public static final AtomicReference<StartupRecord> SEEN_IN_BEFORE_EACH = new AtomicReference<>();

    @Override
    public void beforeAll(TestContext testContext) {

3.4 TestInstanceFactoryPort

Single-impl (optional), ServiceLoader. Produces the test-instance JUnit will use. When present, JUnit receives the bean instance the implementation produces; when absent, jawelte falls back to testClass.getDeclaredConstructor().newInstance(). cdi-module ships an impl that does CDI.current().select(testClass).get() so test classes participate in CDI-managed lifecycle (private fields, package-private classes, JUnit's PER_METHOD all keep working).

Custom implementations replace the default; ServiceLoader rejects multiple impls, so a listing demonstrating the port runs without cdi-module on the classpath and supplies its own TestBeanContainerPort too.

listing core · test-instance-factorylistings/core/19-test-instance-factory/
// src/test/java/example/factory/RecordingTestInstanceFactory.java
public class RecordingTestInstanceFactory implements TestInstanceFactoryPort {

    public static final List<Class<?>> INSTANTIATED = new CopyOnWriteArrayList<>();

    @Override
    public Object createInstance(Class<?> testClass) {
        INSTANTIATED.add(testClass);
        try {
            var constructor = testClass.getDeclaredConstructor();
            constructor.setAccessible(true);
            return constructor.newInstance();
        } catch (ReflectiveOperationException e) {
            throw new RuntimeException("Failed to instantiate " + testClass.getName(), e);
        }
    }
}

// src/test/resources/META-INF/services/org.os890.jawelte.core.api.port.TestInstanceFactoryPort

3.5 BeanScopeMapper + BeanScopeMapperPort

Two related ports for declarative CDI scope rewriting at ProcessAnnotatedType time.

  • BeanScopeMapper — multi-impl, ServiceLoader. Each provider names a trigger annotation (trigger()) and a target scope (targetScope()). The fixed CDI extension in core/impl walks the providers — ordered by the active ServicePriorityResolver (lowest @Priority first, providers without @Priority last, class-name tiebreak) — for every type the CDI runtime delivers and, on the first whose trigger is directly present, removes the type's directly-declared CDI scopes and adds the target. Because the walk is priority-ordered, a consumer overrides a built-in remap for a shared trigger by shipping a higher-precedence (lower-numeric @Priority) provider — the same selection rule as every other multi-impl SPI.
  • BeanScopeMapperPort — single-impl, loaded via TestContext.loadService. The driven port that the fixed CDI extension delegates to. Default impl iterates the BeanScopeMapper providers; replace this port to install an entirely custom remap policy.

A realistic use case: a web-tier bean is @SessionScoped in production, but a plain unit test has no servlet session context, so the bean is unusable as-is. A BeanScopeMapper on the test classpath rewrites the scope to @RequestScoped — which jawelte activates around every @Test method — and the same production source runs in tests with no code change. (scope-module ships this kind of remap as its built-in defaults; the listing below shows the SPI without depending on scope-module.)

listing core · bean-scope-mapperlistings/core/14-bean-scope-mapper/
// src/main/java/example/scopemap/UserPreferences.java   (production web-tier bean)
@SessionScoped
public class UserPreferences implements Serializable {

    private String themeName = "default";

    public String getThemeName() { return themeName; }
    public void setThemeName(String themeName) { this.themeName = themeName; }
}

// src/test/java/example/scopemap/SessionToRequestScopedMapper.java
public class SessionToRequestScopedMapper implements BeanScopeMapper {

    @Override
    public Class<? extends Annotation> trigger() {
        return SessionScoped.class;
    }

    @Override
    public Class<? extends Annotation> targetScope() {
        return RequestScoped.class;
    }
}

// src/test/resources/META-INF/services/org.os890.jawelte.core.api.port.BeanScopeMapper
example.scopemap.SessionToRequestScopedMapper

// src/test/java/example/scopemap/BeanScopeMapperTest.java   (verifies both the SPI rewrite and the user-visible effect)
@EnableTestBeans
class BeanScopeMapperTest {

    @Inject
    BeanManager beanManager;

    @Inject
    UserPreferences userPreferences;

    @Test
    void sessionScopedBeanIsRemappedToRequestScoped() {
        Set<Bean<?>> beans = beanManager.getBeans(UserPreferences.class);
        assertThat(beans.iterator().next().getScope())
                .as("scope was rewritten from @SessionScoped to @RequestScoped at ProcessAnnotatedType time")
                .isEqualTo(RequestScoped.class);
    }

    @Test
    void remappedBeanIsInjectableAndUsableInsideATestMethod() {
        // Under the original @SessionScoped, this injection would have no active
        // context in a plain unit test (no servlet session). After the remap, the
        // bean rides on @RequestScoped — activated by jawelte around every @Test —
        // and is usable like any other CDI bean.
        userPreferences.setThemeName("dark");
        assertThat(userPreferences.getThemeName()).isEqualTo("dark");
    }
}

The listing demonstrates the everyday BeanScopeMapper provider; almost no consumer replaces the driven BeanScopeMapperPort itself. The override pattern is the standard single-impl shape (META-INF/services/...BeanScopeMapperPort naming an FQCN with a public no-arg constructor) — do this only if you need to bypass the provider loop entirely (e.g. to plug a different annotation-rewrite algorithm).

3.6 ConfigResolver

Single active impl, CDI bean (NOT ServiceLoader). Resolves config keys to their raw String values. @ConfigBean classes inject it and call resolve(dotKey). The default impl in core/impl looks up via MicroProfile Config with the documented two-step fallback (dotKey first, then the underscore variant if and only if dotKey contained at least one .).

Users override with an @Alternative @Priority(...) CDI bean — CDI 4's globally-enabled alternative rule selects the highest-priority alternative over the framework default (which carries no @Alternative).

listing core · config-resolverlistings/core/15-config-resolver/
@ApplicationScoped
@Alternative
@Priority(100)
public class FixedConfigResolver implements ConfigResolver {

    private static final Map<String, String> FIXED_VALUES = Map.of(
            "app.greeting", "hello-from-test-resolver");

    @Override
    public Optional<String> resolve(String dotKey) {
        return Optional.ofNullable(FIXED_VALUES.get(dotKey));
    }

    @Override
    public Iterable<String> resolveKeys() {
        return FIXED_VALUES.keySet();
    }

    @Override
    public List<String> resolveAliasKeysFor(String logicalKey) {
        return List.of();
    }
}

3.7 ConfigKeyAliasProvider

Multi-impl, ServiceLoader. The way a non-owning module contributes module-specific MP Config keys to a logical configuration key owned by another module. The owning module reads its own key directly and merges the contributor keys this port returns into the final value. The concrete cross-module wiring lives in the docs of the contributing modules.

Shape: implement aliasesFor(logicalKey), register via META-INF/services, and ship a contributor MP Config key with the actual value. The owner reads its own key + every alias key the resolver returns, then merges.

listing core · config-key-alias-providerlistings/core/20-config-key-alias-provider/
// src/test/java/example/aliasprovider/ShippingFeaturesAliasProvider.java
public class ShippingFeaturesAliasProvider implements ConfigKeyAliasProvider {

    static final String LOGICAL_KEY = "app.features.enabled-flags";

    public static final String SHIPPING_KEY = "app.shipping.features.enabled-flags";

    @Override
    public List<String> aliasesFor(String logicalKey) {
        if (LOGICAL_KEY.equals(logicalKey)) {
            return List.of(SHIPPING_KEY);
        }
        return List.of();
    }
}

// src/test/resources/META-INF/services/org.os890.jawelte.core.api.port.ConfigKeyAliasProvider
example.aliasprovider.ShippingFeaturesAliasProvider

// src/test/resources/META-INF/microprofile-config.properties
app.features.enabled-flags          = beta-checkout,new-search
app.shipping.features.enabled-flags = next-day-delivery,tracking-v2

// src/test/java/example/aliasprovider/AliasProviderTest.java
@Test
void ownerMergesItsOwnValueWithContributorValues() {
    List<String> merged = new ArrayList<>();
    configResolver.resolve("app.features.enabled-flags").ifPresent(v -> merged.addAll(split(v)));
    for (String aliasKey : configResolver.resolveAliasKeysFor("app.features.enabled-flags")) {
        configResolver.resolve(aliasKey).ifPresent(v -> merged.addAll(split(v)));
    }
    assertThat(merged).containsExactly(
            "beta-checkout", "new-search",
            "next-day-delivery", "tracking-v2");
}

The provider lists only the contributor key — not the owner's own key. The owner is responsible for reading its own value directly; resolveAliasKeysFor exists so the owner doesn't need to know which modules might contribute. New contributing modules drop in by shipping their own provider + key without the owner changing a line.

3.8 ServicePriorityResolver

Single active impl, bootstrap via MP Config. The project-wide canonical mechanism for ordering provider lists. Replace it via the MP Config bootstrap key org.os890.jawelte.core.api.port.ServicePriorityResolver — value is the FQCN of an impl class with a public no-arg constructor.

Scope of effect: the resolver applies only to ports loaded through TestContext.loadService(Class) — cdi-module's MockFactory / WhitelistFilter, content-diff's matchers, jpa-module's TransactionStrategy, and so on. It does not apply to TestModuleLifecyclePort, which core's own DelegatingJUnitExtension sorts via a hardcoded PriorityComparator at bootstrap. So swapping the resolver shifts which provider wins for resolver-driven SPIs, but lifecycle ordering across modules is unaffected.

listing core · priority-resolverlistings/core/16-priority-resolver/
public class ReversePriorityResolver implements ServicePriorityResolver {

    @Override
    public <T> List<T> sort(List<T> providers) {
        List<T> copy = new ArrayList<>(providers);
        copy.sort(Comparator.comparingInt(ReversePriorityResolver::priorityOf).reversed());
        return copy;
    }

    private static int priorityOf(Object provider) {
        Priority priority = provider.getClass().getAnnotation(Priority.class);
        return priority == null ? Integer.MIN_VALUE : priority.value();
    }
}

// surefire argLine: -Dorg.os890.jawelte.core.api.port.ServicePriorityResolver=...ReversePriorityResolver

4. @ConfigBean — typed config facade pattern

This section ships at the back of the page on purpose: @ConfigBean is a usage pattern layered on top of CDI + jawelte's ConfigResolver port — not a core mechanism the framework depends on. The two listings below show the canonical shape and a realistic multi-key variant. Everything they do can also be written by hand with a plain @ApplicationScoped class injecting ConfigResolver; the value of @ConfigBean is the convention, not the machinery.

@ConfigBean is a CDI @Stereotype that meta-applies @ApplicationScoped. A class annotated @ConfigBean is therefore a regular CDI bean with application scope; the user does not declare @ApplicationScoped explicitly.

The intended usage pattern is to @Inject the ConfigResolver port into a @ConfigBean class and expose one public method per config key. Each method delegates the raw lookup to the resolver and is responsible for parsing / converting the String value and supplying a meaningful default.

The annotation defines no interceptors and no additional behavior beyond the stereotype's scope contribution. It also serves as a discovery marker so that, for example, limitToTestBeans can identify config beans.

canonical shape — String + int with defaults

One @Inject ConfigResolver, one public getter per key. Each getter parses, applies its own default, and is the only place that knows the raw key string.

listing core · config-beanlistings/core/05-config-bean/
// src/main/java/example/configbean/AppConfig.java
@ConfigBean
public class AppConfig {

    @Inject
    ConfigResolver resolver;

    public String greeting() {
        return resolver.resolve("app.greeting").orElse("hi");
    }

    public int retries() {
        return resolver.resolve("app.retries").map(Integer::parseInt).orElse(3);
    }
}

// src/main/resources/META-INF/microprofile-config.properties
app.greeting = hello from MicroProfile Config
app.retries  = 5

realistic shape — multiple typed keys + required-key validation

Production config beans usually expose several keys with mixed types (Duration, double, boolean, …) and fail fast at startup when a required key is missing. A @PostConstruct guard is the idiomatic place — it runs once per bean lifetime, before any injection-point consumer sees the config bean. The defaults belong inside each getter, kept next to their key.

listing core · config-bean-multi-keylistings/core/18-config-bean-multi-key/
// src/test/java/example/backoff/BackoffConfig.java
@ConfigBean
public class BackoffConfig {

    @Inject
    ConfigResolver resolver;

    @PostConstruct
    void validate() {
        if (resolver.resolve("app.backoff.max-retries").isEmpty()) {
            throw new IllegalStateException(
                    "Required config key 'app.backoff.max-retries' is not set");
        }
    }

    /** Required — @PostConstruct throws if missing. */
    public int maxRetries() {
        return resolver.resolve("app.backoff.max-retries").map(Integer::parseInt).orElseThrow();
    }

    /** Default 100 ms. */
    public Duration initialDelay() {
        return resolver.resolve("app.backoff.initial-delay")
                .map(Duration::parse)              // ISO-8601: PT0.25S, PT500MS
                .orElse(Duration.ofMillis(100));
    }

    /** Default 2.0. */
    public double factor() {
        return resolver.resolve("app.backoff.factor").map(Double::parseDouble).orElse(2.0);
    }

    /** Default true (feature flag). */
    public boolean enabled() {
        return resolver.resolve("app.backoff.enabled").map(Boolean::parseBoolean).orElse(true);
    }
}

// src/main/resources/META-INF/microprofile-config.properties
app.backoff.max-retries   = 5
app.backoff.initial-delay = PT0.25S
app.backoff.factor        = 1.5
app.backoff.enabled       = true

Three patterns to notice. Typed conversion happens in the getter, not in ConfigResolver — the resolver always returns a raw Optional<String>. Defaults live with their key, inside the getter that uses them, so changing a default is a one-line edit. Required-key validation is concentrated in @PostConstruct, not scattered across the getters — a missing required key fails container startup, not the first request that happens to read it.
