db-testdata-module is the seeding-and-verification engine that sits behind testcontrol-module's @TestControl(testData). Two fluent entry points: DbSeed writes a dataset into the database; DbDiff reads the database back and asserts it matches an expected dataset. Either can be called directly from a test method when the declarative @TestControl wrapper would be overkill.

1. quick-start

1.1 purpose

Hand-rolling database fixtures is a known time sink — INSERT statements with the right PK ordering, DELETE statements for cleanup, brittle assertions on the result. db-testdata-module ships dbunit-backed defaults that take a single XML file and translate it into the right SQL shape for your scenario: clean-insert (DELETE + INSERT), insert-only, update-only, refresh (upsert). On the read side, DbDiff reads back what's actually in the table and names the exact row+column that diverged from the expected file.

1.2 hello-world

One @Entity in src/main, an @Test @Transactional method that calls DbSeed then DbDiff.

listing db-testdata-module/01 · hello-worldlistings/db-testdata-module/01-hello-world/
// src/test/resources/products/dbIn.xml
<dataset>
    <PRODUCT ID="1" NAME="apple"/>
    <PRODUCT ID="2" NAME="banana"/>
    <PRODUCT ID="3" NAME="cherry"/>
</dataset>

// src/test/java/example/dbtestdata/ProductsTest.java
@EnableTestBeans
@PersistenceConfig(persistenceUnitName = "productsPU")
class ProductsTest {

    @Test
    @Transactional
    void dbSeedClearsAndInsertsThenDbDiffPasses() {
        DbSeed.forPersistenceUnit()
                .dataset("products/dbIn.xml")
                .cleanInsert()
                .execute();

        DbDiff.forPersistenceUnit()
                .expected("products/dbExpected.xml")
                .assertEquals();
    }
}

2. detailed

2.1 DbSeed

DbSeed opens a dataset (classpath resource or inline string), interpolates EL expressions, and runs it against the database in one of four SeedModes:

Builder methodSeedModeWhat happens
.cleanInsert() (default)CLEAN_INSERTDELETE every row in the dataset's tables in reverse-FK order, then INSERT the dataset rows.
.insert()INSERTINSERT only; duplicate PK throws.
.update()UPDATEUPDATE existing rows by PK; missing PK throws.
.refresh()REFRESHUpsert by PK. Safe under circular FK dependencies because no DELETE step fires.

Builders are single-use. The dataset is either a classpath path (.dataset("path/to/file.xml")) or an inline string (.datasetContent("...")); the two are mutually exclusive. .withValues(Map) attaches EL bindings (see 2.4).

listing db-testdata-module/02 · seed-modeslistings/db-testdata-module/02-seed-modes/
// src/test/java/example/seedmodes/SeedModesTest.java
@Test
@Transactional
void cleanInsertThenRefreshUpserts() {
    DbSeed.forPersistenceUnit().dataset("products/initial.xml").cleanInsert().execute();
    DbSeed.forPersistenceUnit().dataset("products/refresh.xml").refresh().execute();

    // refresh upserts: id=1 untouched, id=2 renamed, id=3 inserted -> 3 rows total.
    Long count = entityManager.createQuery("SELECT COUNT(p) FROM Product p", Long.class).getSingleResult();
    assertThat(count).isEqualTo(3L);
}

2.2 DbDiff

DbDiff reads the current database state, reads the expected dataset, compares both row-by-row + column-by-column, and either passes silently or raises an AssertionError that names the exact diverging cell.

Builder methodEffect
.expected("path.xml") / .expectedContent("...")The expected dataset. Mutually exclusive.
.ignoring("PRODUCT.LAST_MODIFIED", "*.AUDIT_TS")Skip these columns from the diff. Supports table+column or wildcard.
.subsetOnly()Allow the database to contain rows not in the expected file; only assert the expected rows are present.
.unorderedTables("ORDERS")For tables without a meaningful row order, compare as multisets.
.withValues(Map) / .withBean(name, instance) / .withFunction(...)EL bindings, beans, and static functions usable in ${...} expressions and predicate cells.
.assertEquals()Run the comparison. Use .assertRowCount(table, n) for a quick count-only check.
listing db-testdata-module/03 · dbdiff-ignoringlistings/db-testdata-module/03-dbdiff-ignoring/
// dbIn.xml seeds real timestamps; dbExpected.xml has sentinel "9999-01-01..." timestamps.
@Test @Transactional
void ignoringSkipsTheNoisyColumn() {
    DbSeed.forPersistenceUnit().dataset("orders/dbIn.xml").cleanInsert().execute();

    DbDiff.forPersistenceUnit()
            .ignoring("ORDER_ROW.LAST_MODIFIED")
            .expected("orders/dbExpected.xml")
            .assertEquals();
}

2.3 factory choice

Both DbSeed and DbDiff ship four entry-point factories. Pick the one that matches how the calling test resolves its database connection:

FactorySource of the JDBC connection
forConnection(connection)The supplied JDBC connection. db-testdata-module never closes / commits / rolls it back — you own the lifecycle.
forPersistenceUnit()Reads @PersistenceConfig(persistenceUnitName) off the active test class. Non-empty → named PU; empty → delegate to forCurrentPersistenceUnit().
forCurrentPersistenceUnit()The single PU currently active on the calling thread (via PersistenceUnitConnectionResolver). Zero or multiple active PUs raise IllegalStateException.
forPersistenceUnit(name)Explicitly named PU, regardless of annotation.

2.4 EL interpolation

Dataset cells (and column values in DbDiff's predicate columns) may contain ${expression}. The expressions resolve against:

  • Values passed via .withValues(Map) — resolved by key.
  • Beans passed via .withBean(name, instance) — method calls / property reads against the bean.
  • Functions passed via .withFunction(prefix, name, sourceClass, methodName) — called as ${prefix:name(args)}. The source class is reflected for a public-static method with that name; missing or non-static raises an explicit error before the dataset runs.

Predicate cells in DbDiff's expected file (e.g. ${value > 0}) evaluate the expression against the actual cell from the database and pass when the predicate returns true; NULL handling mirrors EL's standard semantics.

listing db-testdata-module/04 · el-interpolationlistings/db-testdata-module/04-el-interpolation/
// src/test/resources/customers/dbIn.xml
<dataset>
    <CUSTOMER ID="${customerId}" NAME="${customerName}"/>
</dataset>

// src/test/java/example/elinterp/InterpolationTest.java
@Test @Transactional
void elPlaceholdersAreResolvedAtSeedTime() {
    DbSeed.forPersistenceUnit()
            .dataset("customers/dbIn.xml")
            .withValues(Map.of("customerId", 42, "customerName", "Alice"))
            .cleanInsert()
            .execute();

    Object name = entityManager.createNativeQuery("SELECT NAME FROM CUSTOMER WHERE ID=42").getSingleResult();
    assertThat(name).isEqualTo("Alice");
}

One dataset file, parameterised through .withValues(Map) — different test methods seed different concrete rows without producing new XML files. Add jakarta.el-api + an EL provider (Tomcat's tomcat-embed-el here) to the test classpath.

3. spi / port reference

db-testdata-module ships three ports, all resolved through core's ServicePriorityResolver + ServiceLoader chain:

PortDefaultPurpose
DbSeedEnginedbunit-XML driver in db-testdata-module-implTakes a dataset string + SeedSpec(mode) and writes it to the connection. Add a custom engine to support a non-XML format (CSV, JSON, Avro) by returning a different value from format() and matching the .format("custom") builder call.
DbDiffEnginedbunit-XML diff in db-testdata-module-implReads the database, compares against the expected content, returns a list of Difference records. Override for a custom comparison strategy (looser equality, schema-aware tolerances).
ELInterpolatorJakarta-EL-backed impl in db-testdata-module-implInterpolates ${...} expressions and evaluates predicate cells. Replace to use a different expression language entirely.
PersistenceUnitNameSupplierCDI bean populated from @PersistenceConfigResolves "which PU should forPersistenceUnit() use?" at static-factory time. Test scenarios that need to force a different PU per-test override this CDI bean rather than reaching into the annotation.

All four use the same ServiceLoader + ServicePriorityResolver selection model as the rest of jawelte — ship a higher-priority impl on the test classpath and it wins automatically.
