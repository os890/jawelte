jta-module is the “turn jpa-module's transactions into real JTA transactions” module. Drop it on the test classpath, add one of three transaction-manager jars, and your @Transactional code runs under JTA semantics — suspending, resuming, and crossing resource managers exactly the way the production app server would do it. No code change in the tests; the swap is purely a dependency-set choice.

1. quick-start

1.1 purpose

jpa-module's default transaction strategy is RESOURCE_LOCAL: one persistence-unit transaction at a time, no cross-resource enlistment, no two-phase commit. That's enough for most tests, but anything that needs more — a write to two persistence units in one transaction, an XA-enrolled message queue, a code path that relies on UserTransaction — needs JTA. jta-module swaps the strategy out via @Priority so the rest of the framework keeps working without changes; the new strategy talks JTA underneath.

1.2 hello-world

An @ApplicationScoped service whose method is @Transactional, plus a persistence.xml with transaction-type="JTA". The test method itself is not @Transactional — the transaction boundary lives inside the service, exactly as it would in production. Each @Transactional service call opens a fresh JTA transaction and commits on return.

listing jta-module/01 · hello-worldlistings/jta-module/01-hello-world/
// src/main/java/example/jta/Customer.java
@Entity
public class Customer {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;
    public Customer() {}
    public Customer(String name) { this.name = name; }
    public Long getId() { return id; }
    public String getName() { return name; }
}

// src/main/java/example/jta/CustomerService.java
@ApplicationScoped
public class CustomerService {

    @Inject
    private EntityManager entityManager;

    public CustomerService() {
    }

    @Transactional
    public Long createCustomer(String name) {
        Customer customer = new Customer(name);
        entityManager.persist(customer);
        return customer.getId();
    }

    @Transactional
    public long countCustomers() {
        return entityManager
                .createQuery("SELECT COUNT(c) FROM Customer c", Long.class)
                .getSingleResult();
    }
}

// src/test/java/example/jta/CustomerServiceTest.java
/**
 * Hello-world for jta-module: the test method itself is NOT
 * @Transactional. The transaction boundary lives inside CustomerService,
 * exactly as it would in production code. Each @Transactional call
 * begins a fresh JTA transaction; on commit, the next @Transactional
 * read sees the row.
 */
@EnableTestBeans
class CustomerServiceTest {

    @Inject
    private CustomerService customerService;

    @Test
    void transactionalServiceCallCommitsAndIsVisibleToTheNextCall() {
        Long generatedId = customerService.createCustomer("Alice");
        assertThat(generatedId)
                .as("createCustomer's JTA transaction committed and assigned a generated id")
                .isNotNull();

        assertThat(customerService.countCustomers())
                .as("a fresh JTA read sees the row the previous @Transactional committed")
                .isEqualTo(1L);
    }
}

The matching persistence.xml declares transaction-type="JTA"; the JPA provider then asks the active TransactionManager (which jta-module publishes via JNDI) to join the EntityManager into the current transaction.

src/test/resources/META-INF/persistence.xmllistings/jta-module/01-hello-world/src/test/resources/META-INF/persistence.xml
<persistence-unit name="customersPU" transaction-type="JTA">
    <provider>org.hibernate.jpa.HibernatePersistenceProvider</provider>
    <exclude-unlisted-classes>false</exclude-unlisted-classes>
    <properties>
        <property name="jakarta.persistence.jdbc.driver" value="org.h2.Driver"/>
        <property name="jakarta.persistence.jdbc.url"
                  value="jdbc:h2:mem:jtaCustomers;MODE=LEGACY;DB_CLOSE_DELAY=-1"/>
        <property name="jakarta.persistence.jdbc.user" value="sa"/>
        <property name="jakarta.persistence.jdbc.password" value=""/>
        <property name="hibernate.hbm2ddl.auto" value="create-drop"/>
    </properties>
</persistence-unit>

What changed compared to jpa-module's hello-world: nothing in the user-facing code shape. The bean still injects EntityManager, the method is still annotated @Transactional. The two visible differences are the persistence.xml attribute (JTA instead of RESOURCE_LOCAL) and the dependency list (jta-module + a TM + a JNDI provider, see 1.3).

1.3 maven setup

jta-module's api / impl, a JTA TM jar (Geronimo here), and a JNDI provider. xbean-naming is the lightest free JNDI implementation; any other registered InitialContextFactory works.

2. detailed

2.1 priority-based selection

jpa-module ships a default TransactionStrategy at the lowest priority. jta-module ships JtaTransactionStrategy at a higher priority. Both are registered as ServiceLoader providers; the active resolver picks the highest-priority one whenever TestContext.loadService(TransactionStrategy.class) runs. So:

  • core + cdi-module + jpa-module on the classpath → RESOURCE_LOCAL active.
  • Add jta-module to the classpath → JTA active. No annotation change in the tests, no persistence.xml rewrite (transaction-type stays whatever you want it; the strategy doesn't care).
  • Remove jta-module → back to RESOURCE_LOCAL.

This is the same priority-resolver pattern documented in core docs section 3.8; jta-module is the canonical example of one module shadowing another via priority.

programmatic UserTransaction

When you need a transaction boundary outside of @Transactional — e.g. a setup helper that has to run partially inside a tx and partially outside — inject UserTransaction. jta-module exposes it as a CDI bean wired to the same TransactionManager the @Transactional interceptor drives.

listing jta-module/02 · user-transactionlistings/jta-module/02-user-transaction/
// src/test/java/example/usertx/UserTransactionTest.java
/**
 * Programmatic UserTransaction. jta-module exposes UserTransaction as
 * a CDI bean wired to the same TransactionManager the @Transactional
 * interceptor drives — so begin/commit/rollback by hand have the same
 * effect on the database as the annotation.
 */
@EnableTestBeans
class UserTransactionTest {

    @Inject
    UserTransaction userTransaction;

    @Inject
    EntityManager entityManager;

    @Test
    void beginCommitPersistsAndIsVisibleToTheNextTransaction() throws Exception {
        assertThat(userTransaction.getStatus()).isEqualTo(Status.STATUS_NO_TRANSACTION);

        userTransaction.begin();
        try {
            assertThat(userTransaction.getStatus()).isEqualTo(Status.STATUS_ACTIVE);
            entityManager.persist(new Marker());
            userTransaction.commit();
        } catch (RuntimeException unexpected) {
            if (userTransaction.getStatus() != Status.STATUS_NO_TRANSACTION) {
                userTransaction.rollback();
            }
            throw unexpected;
        }

        userTransaction.begin();
        try {
            long count = entityManager
                    .createQuery("SELECT COUNT(m) FROM Marker m", Long.class)
                    .getSingleResult();
            assertThat(count).isEqualTo(1L);
        } finally {
            userTransaction.commit();
        }
    }
}

The listing adds narayana-jta to the test classpath alongside Geronimo. Geronimo is still the TM (bound via JNDI by jta-module's JndiArtifactBinder); uber-Narayana supplies the CDI @TransactionScoped integration that activates the EntityManager's transaction-scoped context when the TM signals begin/commit.

@TransactionScoped CDI bean

A @TransactionScoped bean lives one instance per JTA transaction. The instance is created lazily on first dereference inside the transaction and destroyed (with @PreDestroy) when the transaction completes — on both commit and rollback. The jpa-module's EntityManager proxy is itself a @TransactionScoped bean.

listing jta-module/03 · transaction-scoped-beanlistings/jta-module/03-transaction-scoped-bean/
// src/test/java/example/txscoped/PerTxBean.java
/**
 * @TransactionScoped bean: one instance per JTA transaction. The
 * per-instance UUID lets the test see two transactions produce two
 * different bean instances. The @PreDestroy counter proves the bean
 * is destroyed when the transaction completes.
 */
@TransactionScoped
public class PerTxBean implements Serializable {

    public static final AtomicInteger PRE_DESTROY_COUNT = new AtomicInteger();

    private final String id = UUID.randomUUID().toString();

    public String getId() {
        return id;
    }

    @PreDestroy
    void onPreDestroy() {
        PRE_DESTROY_COUNT.incrementAndGet();
    }
}

// src/test/java/example/txscoped/PerTxBeanReader.java   (provides the @Transactional boundary)
@ApplicationScoped
public class PerTxBeanReader {

    @Inject
    PerTxBean perTxBean;

    @Transactional
    public String readIdInsideJtaTx() {
        return perTxBean.getId();
    }
}

// src/test/java/example/txscoped/PerTxBeanTest.java
@EnableTestBeans
class PerTxBeanTest {

    @Inject
    PerTxBeanReader reader;

    @Test
    void eachJtaTransactionGetsItsOwnInstance() {
        PerTxBean.PRE_DESTROY_COUNT.set(0);

        String firstTxId = reader.readIdInsideJtaTx();
        String secondTxId = reader.readIdInsideJtaTx();

        assertThat(firstTxId).isNotBlank();
        assertThat(secondTxId).isNotBlank().isNotEqualTo(firstTxId);
        assertThat(PerTxBean.PRE_DESTROY_COUNT.get())
                .as("@PreDestroy fired once for the first tx and once for the second")
                .isEqualTo(2);
    }
}

2.2 picking a transaction manager

jta-module doesn't ship a transaction manager itself — just the integration glue. Choose one of three based on your project:

  • Geronimo (org.apache.geronimo.components:geronimo-transaction) — lightest, fewest moving parts, the default in jawelte's own test sweep. Good for tests that just need JTA semantics, not the full XA recovery story.
  • Narayana (org.jboss.narayana.jta:narayana-jta) — full XA, used inside WildFly. Reach for it when your production runtime is Narayana-based and you want maximum fidelity in tests.
  • Atomikos (com.atomikos:atomikos-util + the Jakarta-namespace classifier artifacts) — another XA-capable choice with its own configuration surface; jta-module's TransactionManagerProvider SPI lets you supply an Atomikos-specific provider (no concrete pom fragment in this listing set yet).

All three publish their TransactionManager via JNDI; jta-module's JndiArtifactBinder looks the TM up at startup via a known set of JNDI names. You need some JNDI provider on the classpath for the lookup to resolve — xbean-naming is the easiest; any other InitialContextFactory works.

3. spi / port reference

jta-module ships one port:

TransactionManagerProvider

Single active impl, ServiceLoader + priority. Returns the live TransactionManager. Default impl looks up the TM via JNDI under a set of well-known names (jta-module's JndiArtifactBinder publishes the TM under those names at startup). Override to short-circuit the JNDI lookup — useful when you want to share one TM across multiple jawelte test runs or feed in a pre-configured TM with custom timeouts, recovery managers, or interceptors.

listing jta-module/04 · transaction-manager-providerlistings/jta-module/04-transaction-manager-provider/
// src/test/java/example/tmprovider/RecordingTransactionManagerProvider.java
@Priority(1)
public class RecordingTransactionManagerProvider implements TransactionManagerProvider {

    public static final AtomicInteger CREATE_COUNT = new AtomicInteger();

    @Override public String name() { return "recording-geronimo"; }

    @Override
    public boolean isAvailable() {
        return loadable("org.apache.geronimo.transaction.manager.GeronimoTransactionManager");
    }

    @Override
    public TransactionManager create() {
        CREATE_COUNT.incrementAndGet();
        // build / cache Geronimo's TM via reflection (see listing source for the full impl)
        ...
    }

    // userTransaction(), transactionSynchronizationRegistry(), shutdown() implemented the same way
}

// src/test/resources/META-INF/services/org.os890.jawelte.module.jta.api.port.TransactionManagerProvider
example.tmprovider.RecordingTransactionManagerProvider

The default AutoSelectTransactionManagerProvider carries @Priority(Integer.MAX_VALUE); @Priority(1) on the custom impl wins the sort and becomes the active provider. The test injects UserTransaction, calls begin/commit, then asserts CREATE_COUNT > 0 — proof that the custom create() was invoked.

Everything else jta-module adds (the JtaTransactionStrategy itself, the JNDI binder, the persistence-property override that switches Hibernate to JTA mode) is internal — the user-facing customization knob is the TM choice plus this one port.
