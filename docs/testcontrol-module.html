testcontrol-module collapses the per-method fixture setup into a single annotation. @TestControl on a @Test method declares which test-data folders to seed and verify, which scope-module scopes to allow, and a safety guard against silently-passing tests — replacing what would otherwise be a noisy @BeforeEach / @AfterEach block.

1. quick-start

1.1 purpose

Most test-fixture work is the same three steps: load some rows into the database, run the test method, assert the resulting rows match an expected dataset. Repeating that scaffolding across every test method makes the test class noisy and the actual assertion hard to spot. @TestControl(testData = "...") takes the entire pipeline — seed → update → commit → verify — and runs it from one classpath folder, so the test method body holds only the assertion that's specific to the method.

1.2 hello-world

One annotation, one folder, two XML files. dbIn/greetings.xml clean-inserts the seed rows before the test method; dbExpected/greetings.xml is asserted against the live DB after. The test method body itself can be empty — the framework runs both halves.

The test class below stacks three annotations from three modules: @EnableTestBeans (core, boots the CDI container per test class), @PersistenceConfig (jpa-module, picks the persistence unit), and @TestControl (testcontrol's own contribution, declares the testdata folder). The other two are documented on their own module pages; everything below explains @TestControl.

listing testcontrol-module/01 · hello-worldlistings/testcontrol-module/01-hello-world/
// src/test/resources/testdata/greetings/dbIn/greetings.xml
<dataset>
    <GREETING ID="1" TEXT="hello"/>
    <GREETING ID="2" TEXT="hi"/>
</dataset>

// src/test/resources/testdata/greetings/dbExpected/greetings.xml
<dataset>
    <GREETING ID="1" TEXT="hello"/>
    <GREETING ID="2" TEXT="hi"/>
</dataset>

// src/test/java/example/testcontrol/GreetingsTest.java
@EnableTestBeans
@PersistenceConfig(persistenceUnitName = "greetingsPU")
class GreetingsTest {

    @Test
    @TestControl(testData = "testdata/greetings")
    void seedFromDbInAndVerifyAgainstDbExpected() {
    }
}

The test method body is empty — testcontrol seeds from dbIn/ in beforeEach and runs DbDiff against dbExpected/ in afterEach. The shape generalises: change the test method body to exercise the system under test, change dbExpected/ to the post-condition you want to assert.

1.3 maven setup

testcontrol-module is a meta-module: by itself it manipulates the lifecycle, but it relies on companion modules for the actual seeding (db-testdata-module) and persistence (jpa-module). All three are usually on the classpath together. The fragment below shows only the testcontrol-module + db-testdata-module deltas; the core-docs maven setup covers jawelte-core + cdi-module + Jakarta APIs + JUnit + AssertJ + CDI runtime, and the jpa-module setup adds the JPA provider + H2 + xbean/asm that testcontrol's seed/verify pipeline drives.

2. detailed

2.1 testData — three-phase pipeline

Each entry in testData = {…} names a classpath folder that may contain any of three sub-directories. testcontrol scans the folders before the test method enters and again after it exits, dispatching the right phase per sub-directory:

Sub-folderPhaseAction
dbIn/*.xmlseed (beforeEach)clean-inserted via db-testdata-module's DbSeed.dataset(xml).cleanInsert()
dbUpdate/*.xmlupdate (beforeEach)updated via DbSeed.dataset(xml).update() — runs after every entry's dbIn/ has been seeded
dbExpected/*.xmlverify (afterEach)asserted via DbDiff.expected(xml).assertEquals()

Files within each sub-folder are processed in alphabetical order. Across multiple testData entries, all dbIn/ phases complete before any dbUpdate/ phase starts, and the same in-order rule applies to dbExpected/ once the test method has returned (every entry's verify phase runs in entry order during afterEach).

listing testcontrol-module/02 · update-phaselistings/testcontrol-module/02-update-phase/
// src/test/resources/testdata/products/dbIn/products.xml
<dataset>
    <PRODUCT ID="1" NAME="old-apple"/>
    <PRODUCT ID="2" NAME="old-banana"/>
</dataset>

// src/test/resources/testdata/products/dbUpdate/products.xml
<dataset>
    <PRODUCT ID="1" NAME="new-apple"/>
    <PRODUCT ID="2" NAME="new-banana"/>
</dataset>

// src/test/resources/testdata/products/dbExpected/products.xml
<dataset>
    <PRODUCT ID="1" NAME="new-apple"/>
    <PRODUCT ID="2" NAME="new-banana"/>
</dataset>

// src/test/java/example/updatephase/ProductsTest.java
@EnableTestBeans
@PersistenceConfig(persistenceUnitName = "productsPU")
class ProductsTest {

    @Test
    @TestControl(testData = "testdata/products")
    void dbInThenDbUpdateThenVerifyAgainstDbExpected() {
    }
}

The empty test-method body is intentional: dbIn seeds the "old" names, dbUpdate switches them to "new", dbExpected confirms the merged state. A real test would mutate further inside the method and the dbExpected would reflect those mutations on top.

2.2 testDataBasePath + MP Config

When every test method in a class lives under a common prefix (e.g. testdata/myclass/m01, m02, …), set the prefix once via @TestControl(testDataBasePath = "testdata/myclass") and let each method name just the trailing slug.

The MicroProfile Config key org.os890.jawelte.module.testcontrol.api.TestControl.base-path overrides the annotation when set to a non-empty value — useful for project-wide conventions like "all test data lives under fixtures/" without editing every test class.

listing testcontrol-module/03 · testdata-basepathlistings/testcontrol-module/03-testdata-basepath/
// src/test/java/example/basepath/ItemsTest.java
@EnableTestBeans
@PersistenceConfig(persistenceUnitName = "itemsPU")
class ItemsTest {

    @Test
    @TestControl(testDataBasePath = "fixtures", testData = "m01")
    void basePathIsAppliedAsPrefixToTestData_m01() {
    }

    @Test
    @TestControl(testDataBasePath = "fixtures", testData = "m02")
    void basePathIsAppliedAsPrefixToTestData_m02() {
    }
}

Folder layout: src/test/resources/fixtures/m01/{dbIn,dbExpected}/ and fixtures/m02/{dbIn,dbExpected}/. Per-method testData entries name just the trailing leaf; the basePath is applied as a prefix before the entry resolves.

2.3 multi-PU routing

An entry can prefix the folder with a persistence-unit name to route it: "ordersPU:testdata/orders" sends the sub-folders to PU ordersPU, while a bare "testdata/customers" uses the default PU. Multiple entries in the same annotation may target different PUs — each phase runs against the entry's own PU. (The listing below uses two named PUs and no default; both entries carry an explicit prefix.)

listing testcontrol-module/04 · multi-pu-routinglistings/testcontrol-module/04-multi-pu-routing/
// persistence.xml declares customersPU and ordersPU.

// src/test/java/example/multipu/MultiPuRoutingTest.java
@EnableTestBeans
class MultiPuRoutingTest {

    @Test
    @TestControl(testData = {
            "customersPU:testdata/customers",
            "ordersPU:testdata/orders"
    })
    void eachTestDataEntryRoutesToItsOwnPersistenceUnit() {
    }
}

The customersPU: prefix sends testdata/customers/dbIn,dbExpected to the customers PU; the ordersPU: prefix routes the other entry to the orders PU. dbExpected on each side verifies the rows landed in the right database; no test method body needed.

2.4 startScopes — scope allow-list

startScopes = {TestMethodScoped.class, ...} declares which scope-module scopes the method allows. testcontrol observes scope-module's BeforeScopeStarted CDI event and vetoes any scope not in the list; the empty default array ({}) means "all scope-module scopes activate normally". Container-managed scopes (@RequestScoped, JPA's @TransactionScoped) never flow through BeforeScopeStarted and therefore stay active regardless of startScopes.

Current behaviour: scope-module's lifecycle adapter fires the BeforeScopeStarted event but does not consult its veto status when deciding whether to activate the scope — the context activates unconditionally afterwards. The veto is observable by your own @Observes BeforeScopeStarted beans and by inspecting event.isVetoed(), which is useful for diagnostics, but a vetoed @TestMethodScoped bean is still injectable today. Consumer-side enforcement (refusing to inject vetoed-scope beans) is deferred to a follow-up ticket in jawelte's roadmap.

2.5 requireDbExpected guard

When a test method declares testData entries, the default requireDbExpected = true demands that at least one entry contributes a dbExpected/*.xml dataset. Without the guard, deleting (or emptying) the dbExpected/ folder of a verifying test would let it pass silently — the verify phase would have nothing to assert against. testcontrol-module's lifecycle adapter checks the condition from its TestModuleLifecyclePort.beforeEach hook and throws an explicit error pointing at the missing assertion side — the failure surfaces during JUnit's beforeEach phase, before the test body runs.

Set requireDbExpected = false per-method only when the test legitimately seeds without verifying (smoke tests, fixture-setup tests that another test consumes). See listing testcontrol-module/06 · require-db-expected for a runnable example.

3. spi / port reference

testcontrol-module ships no SPI / port of its own. Its public API is exactly one annotation (@TestControl). All extension points it exposes are inherited from the modules it composes:

  • How datasets are read & verified — db-testdata-module's DbSeedDataSetReader / DbDiffEngine ports. Swap these to use a non-XML dataset format or change the diff strategy.
  • Which transaction wraps the seed phase — jpa-module's TransactionStrategy port. JTA, JPA-resource-local, or a custom strategy all work.
  • How scope activation gets vetoed — scope-module's BeforeScopeStarted CDI event is the listener side; testcontrol's observer is registered automatically when the impl jar is on the classpath.

The base-path override key org.os890.jawelte.module.testcontrol.api.TestControl.base-path is the only MP Config knob testcontrol itself reads.
