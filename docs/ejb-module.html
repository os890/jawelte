ejb-module lets you keep @jakarta.ejb.Stateless and @jakarta.ejb.Singleton on your production code and run tests against it in plain CDI SE — no application server, no remoting layer, no JNDI naming gymnastics. The module's CDI extension rewrites the EJB annotations into CDI scopes plus an implicit @jakarta.transaction.Transactional at bean-discovery time, so what hits the container looks like a regular CDI bean.

1. quick-start

1.1 purpose

You have a production codebase full of EJB session beans — @Stateless services, @Singleton facades. The production deployment runs inside an EE container that knows what those annotations mean. Unit tests don't run inside an EE container, so the same code can't normally be exercised without an embedded server or a parallel CDI version of every EJB.

ejb-module short-circuits that. With it on the classpath, jawelte's CDI extension sees a class annotated @Stateless or @Singleton, adds the matching CDI scope (@RequestScoped or @ApplicationScoped by default; @TestClassScoped for Singleton when scope-module is also present), and adds @Transactional so transactional semantics match the EE expectation. The bean now is a CDI bean as far as the test runtime is concerned, even though the source declares EJB.

1.2 hello-world

A production @Singleton EJB in src/main, a CDI test that injects it.

listing ejb-module/01 · singletonlistings/ejb-module/01-singleton/
// src/main/java/example/ejb/Greeter.java
@Singleton
public class Greeter {
    public String hello(String name) {
        return "hello, " + name;
    }
}

// src/test/java/example/ejb/GreeterTest.java
@EnableTestBeans
class GreeterTest {

    @Inject
    Greeter greeter;

    @Test
    void ejbSingletonInjects() {
        assertThat(greeter.hello("ejb-module")).isEqualTo("hello, ejb-module");
    }
}

Production code is untouched; @Singleton stays where it is. The test sees a CDI bean because ejb-module's extension added an @ApplicationScoped annotation to the type at ProcessAnnotatedType time.

2. detailed

2.1 annotation mapping

The default mapper rewrites:

  • @jakarta.ejb.Stateless → @RequestScoped (matches the typical "one EJB instance per call" pattern).
  • @jakarta.ejb.Singleton → @ApplicationScoped by default. With scope-module also on the classpath the MP Config key org.os890.jawelte.module.ejb.singleton.default-scope rebinds it to @TestClassScoped — one shared instance per test class instead of one per JVM.

The rewrite happens at ProcessAnnotatedType time; the source class keeps the EJB annotation, the CDI bean carries the mapped scope.

listing ejb-module/02 · statelesslistings/ejb-module/02-stateless/
// src/main/java/example/stateless/Counter.java
@Stateless
public class Counter {
    private int value;
    public int increment() { return ++value; }
}

// src/test/java/example/stateless/CounterTest.java
@Test
void firstMethodSeesFreshCounter() {
    assertThat(counter.increment()).isEqualTo(1);
}

@Test
void secondMethodAlsoSeesFreshCounter() {
    assertThat(counter.increment()).isEqualTo(1);   // @RequestScoped — new instance per method
}

2.2 implicit @Transactional

EJB methods are container-managed transactional by default (REQUIRED). To preserve that semantic without forcing the user to re-annotate every EJB method, the mapper also adds @jakarta.transaction.Transactional to the class when none is present. With jta-module on the classpath that triggers the JTA strategy; with jpa-module only that triggers RESOURCE_LOCAL; either way @Transactional semantics hold.

listing ejb-module/03 · implicit-transactionallistings/ejb-module/03-implicit-transactional/
// src/main/java/example/implicittx/NoteRepository.java
@Stateless
public class NoteRepository {

    @Inject EntityManager entityManager;

    // Note: no @Transactional anywhere; ejb-module's mapper added it.
    public Long save(String body) {
        Note note = new Note(body);
        entityManager.persist(note);
        return note.getId();
    }

    public long count() {
        return entityManager.createQuery("SELECT COUNT(n) FROM Note n", Long.class).getSingleResult();
    }
}

// src/test/java/example/implicittx/NoteRepositoryTest.java
@Test
void persistCommitsWithoutExplicitTransactional() {
    Long id = noteRepository.save("hello");
    assertThat(id).isNotNull();
    assertThat(noteRepository.count()).isEqualTo(1L);
}

2.3 fidelity caveats

This is the part to be honest about: ejb-module is not a 1:1 emulation of a real EE container. What it does cover:

  • Bean discovery + scope assignment.
  • Implicit @Transactional mapping.
  • Regular CDI injection of the EJB into other CDI beans / test classes.

What it does NOT cover:

  • EJB instance pooling (CDI scopes are not pool-aware).
  • Remoting (no @Remote interfaces over RMI / IIOP).
  • Container-managed transaction attributes beyond the default REQUIRED (@TransactionAttribute(REQUIRES_NEW) etc. need to be rewritten as the matching @Transactional rollback policy or a manual interceptor).
  • EJB timer services, asynchronous methods, security context propagation.

For the kind of EJB code that's effectively "a transactional service with a few CRUD methods" — the bulk of session-bean code most projects ship — that's enough.

3. spi / port reference

ejb-module ships one port:

EjbAnnotationMapper

Single active impl, ServiceLoader + priority. Given an EJB-annotated Class<?>, returns the CDI scope to install and (optionally) extra annotations to add. Default impl handles @Stateless + @Singleton as documented above. Override to extend the mapping to @MessageDriven, vendor-specific EJB-like annotations, or to flip the default scopes to something your project's testing conventions prefer.

listing ejb-module/04 · ejb-annotation-mapperlistings/ejb-module/04-ejb-annotation-mapper/
// src/test/java/example/mapper/StatefulAsRequestScopedMapper.java
@Priority(1)
public class StatefulAsRequestScopedMapper implements EjbAnnotationMapper {

    private static final class RequestScopedLiteral
            extends AnnotationLiteral<RequestScoped> implements RequestScoped { }

    @Override
    public List<Annotation> mapBeanMetadata(Class<?> beanClass, BeanManager beanManager) {
        if (beanClass.isAnnotationPresent(Stateful.class)) {
            return List.of(new RequestScopedLiteral());
        }
        return null;   // not handled — fall through to the next mapper / default
    }
}

// src/test/resources/META-INF/services/org.os890.jawelte.module.ejb.api.port.EjbAnnotationMapper
example.mapper.StatefulAsRequestScopedMapper

// src/test/resources/META-INF/microprofile-config.properties
config_ordinal=200
org.os890.jawelte.module.ejb.bean-defining-annotations=\
    jakarta.ejb.Singleton,\
    jakarta.ejb.Stateless,\
    jakarta.ejb.Stateful

Two moving pieces. The mapper claims any @jakarta.ejb.Stateful class and adds @RequestScoped. The MP Config override teaches ejb-module's classpath scan to look for @Stateful — without it the scan only finds @Singleton + @Stateless and your @Stateful classes are never even seen by the CDI extension. Both are required to make a new EJB annotation injectable.
