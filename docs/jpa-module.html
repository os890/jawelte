jpa-module turns "I want to test JPA code" into "@Inject EntityManager". You bring a persistence.xml + entity classes + JPA provider on the test classpath; jpa-module bootstraps the EntityManagerFactory once per JVM, hands out transaction-scoped EntityManagers, wraps your test method in a transaction when you ask, and wipes the tables between methods so the next test starts from a known empty state.

1. quick-start

1.1 purpose

Production JPA code injects an EntityManager, runs queries, persists entities. To unit-test that code you need a real EntityManager connected to a real database for the duration of the test — but you don't want the test to need a running server, leak state between methods, or take ten seconds to warm up. jpa-module sets that up:

  • The EntityManagerFactory is bootstrapped once per JVM (cached by persistence-unit name) so subsequent test classes don't re-pay the startup cost.
  • The EntityManager is @TransactionScoped — one instance per active transaction. The same @Inject EntityManager field flips to a fresh underlying instance every time a new transaction begins.
  • The default backend is H2 in-memory. @PersistenceConfig(fileMode = true) switches to H2 on disk for tests that need durable state.
  • Table cleanup between test methods is automatic in in-memory mode (skipped in file mode — you presumably want the data to stick around).

1.2 hello-world

An entity in src/main, a persistence.xml that names a PU, a test that injects an EntityManager and uses it inside @Transactional.

listing jpa-module/01 · hello-worldlistings/jpa-module/01-hello-world/
// src/main/java/example/jpa/Note.java
@Entity
public class Note {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String text;
    // constructors, accessors omitted
}

// src/main/resources/META-INF/persistence.xml
<persistence version="3.2"
             xmlns="https://jakarta.ee/xml/ns/persistence"
             xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
             xsi:schemaLocation="https://jakarta.ee/xml/ns/persistence https://jakarta.ee/xml/ns/persistence/persistence_3_2.xsd">
  <persistence-unit name="notesPU" transaction-type="RESOURCE_LOCAL">
    <provider>org.hibernate.jpa.HibernatePersistenceProvider</provider>
    <exclude-unlisted-classes>false</exclude-unlisted-classes>
  </persistence-unit>
</persistence>

// src/test/java/example/jpa/NoteTest.java
@EnableTestBeans
class NoteTest {

    @Inject
    EntityManager entityManager;

    @Test
    @Transactional
    void persistAndQuery() {
        entityManager.persist(new Note("hello jpa-module"));
        entityManager.flush();

        Long count = entityManager
                .createQuery("SELECT COUNT(n) FROM Note n", Long.class)
                .getSingleResult();
        assertThat(count).isEqualTo(1L);
    }

    @Test
    @Transactional
    void freshDatabaseEveryTestMethod() {
        Long count = entityManager.createQuery(
                "SELECT COUNT(n) FROM Note n", Long.class).getSingleResult();
        assertThat(count).isZero();
    }
}

persistAndQuery inserts one row and asserts COUNT is 1. freshDatabaseEveryTestMethod asserts the table is empty — proving the inter-method cleanup happens automatically. Order-independent: both methods see what they expect regardless of which one runs first.

2. detailed

2.1 @PersistenceConfig

@PersistenceConfig on the test class switches behaviour from the in-memory default. Four attributes, all optional:

  • fileMode = false — when true, every PU connects to jdbc:h2:file:{filePath}/{puName} instead of in-memory. Per-method table cleanup is skipped (files persist across JVM restarts on purpose).
  • filePath = "" — directory for H2 files in file-mode. Empty means ~/{appLabel}_db/, where appLabel falls back to the test class's simple name if the MP Config key org.os890.jawelte.module.jpa.app-label is unset. Ignored when fileMode=false.
  • persistenceUnits = {} — filter on which PUs from persistence.xml to bootstrap (a list of names). Empty means "all of them".
  • persistenceUnitName = "" — in multi-PU mode, names the single PU the TransactionStrategy eagerly opens on begin(). Empty means the strategy resolves the eager PU itself by looking at the test class's @Inject @Named EntityManager fields.

Easy to confuse: persistenceUnits (plural) is a discovery filter at boot time; persistenceUnitName (singular) picks one of the booted PUs to open eagerly when a transaction begins. They control different things and can be set independently — e.g. boot two PUs but eagerly open only one.

Annotation is @Inherited so a base test class can set the config for a whole hierarchy.

Three common shapes on a test class:

// Single PU with durable state on disk (e.g. for tests that exercise an upgrade script).
@EnableTestBeans
@PersistenceConfig(fileMode = true)
class UpgradeScriptTest { ... }

// Multi-PU mode — bootstrap only the named PU(s) from persistence.xml; eagerly open ordersPU on begin().
@EnableTestBeans
@PersistenceConfig(persistenceUnits = {"ordersPU", "customersPU"}, persistenceUnitName = "ordersPU")
class OrdersAndCustomersTest { ... }

// Default — in-memory H2, all PUs from persistence.xml. Same as omitting @PersistenceConfig altogether.
@EnableTestBeans
@PersistenceConfig
class DefaultsTest { ... }

2.2 transactions & the EntityManager

The EntityManager jawelte hands you via @Inject is a CDI proxy backed by the active TransactionStrategy (default RESOURCE_LOCAL; jta-module switches to JTA via @Priority). The strategy's lifecycle is per-transaction:

  • You annotate the test method @Transactional (or wrap a section in UserTransaction). The strategy's begin() runs first.
  • The first EntityManager method call on the proxy triggers a lazy createEntityManager() on the cached EntityManagerFactory and joins the active transaction.
  • Two @Inject EntityManager lookups inside one transaction return the same underlying instance. The next transaction gets a fresh one.
  • commit() or rollback() closes the EntityManager; jpa-module fires the matching transaction events (section 2.5).

Multi-PU tests qualify each injection point with the PU name — see 2.3.

2.3 multi-PU usage

When the persistence.xml declares more than one <persistence-unit>, jpa-module's CDI extension publishes one synthetic EntityManager / EntityManagerFactory bean per unit, each qualified with @Named(puName). An unqualified @Inject EntityManager fails to resolve in this mode — the qualifier is required so the routing proxy knows which factory to consult.

Two equivalent ways to declare the qualifier on the injection point:

option 1 — @Inject @Named("puName")

The canonical CDI form. Inject either the EntityManager or its EntityManagerFactory for a specific PU by adding @Named(puName) next to @Inject.

listing jpa-module/02 · multi-pulistings/jpa-module/02-multi-pu/
// src/test/java/example/multipu/MultiPuTest.java
@EnableTestBeans
class MultiPuTest {

    @Inject
    @Named("notesPU")
    EntityManager notesEm;

    @Inject
    @Named("auditPU")
    EntityManager auditEm;

    @Inject
    @Named("notesPU")
    EntityManagerFactory notesEmf;

    @Inject
    @Named("auditPU")
    EntityManagerFactory auditEmf;

    @Test
    void namedQualifierRoutesEachInjectionToItsOwnPu() {
        assertThat(notesEmf).isNotSameAs(auditEmf);
        assertThat(notesEm).isNotSameAs(auditEm);
    }

    @Test
    @Transactional
    void crossPuWriteCommitsBothPus() {
        notesEm.persist(new Note("hello"));
        auditEm.persist(new AuditRecord("note.created"));

        Long notesCount = notesEm.createQuery("SELECT COUNT(n) FROM Note n", Long.class).getSingleResult();
        Long auditCount = auditEm.createQuery("SELECT COUNT(a) FROM AuditRecord a", Long.class).getSingleResult();

        assertThat(notesCount).isEqualTo(1L);
        assertThat(auditCount).isEqualTo(1L);
    }
}

option 2 — @PersistenceContext(unitName = "puName")

The standard JPA annotation is rewritten by JpaCdiExtension to @Inject @Named(unitName) during ProcessAnnotatedType. The two forms are equivalent at runtime; pick whichever reads better in your codebase. @PersistenceContext is handy when the same source has to compile both inside and outside a CDI container (jawelte rewrites it; a real Jakarta EE container honours it natively).

multi-PU @PersistenceContext injection
@ApplicationScoped
public class CrossPuService {

    @PersistenceContext(unitName = "ordersPU")
    private EntityManager ordersEm;

    @PersistenceContext(unitName = "customersPU")
    private EntityManager customersEm;

    // jpa-module rewrites both fields to @Inject @Named(...) at bootstrap
}

What the strategy does. Each named EntityManager is a routing proxy that lazy-joins the active transaction the first time you call a method on it; commit() / rollback() closes each joined EM in turn. @PersistenceConfig(persistenceUnitName = "ordersPU") on the test class additionally tells the strategy which PU to eagerly open on begin() — useful when an early observer needs a connection before any EntityManager method has been called.

2.4 @ReadOnly

@ReadOnly on a @Test method (or the test class) marks the test as not-writing. jpa-module's interceptor reacts in three ways under the default ResourceLocalTransactionStrategy: (1) when the test is wrapped by @Transactional, the transaction is marked rollback-only before completion so any persists/merges inside the method never reach the DB; (2) the per-method cleanup (truncate the schema between tests) is skipped — the test is asserted to make no schema-visible mutations, so there's nothing to clean; (3) Hibernate's session-level setDefaultReadOnly(true) hint is set on the joined session so dirty-checking flushes are suppressed for entities loaded in this transaction. Useful for tests that genuinely don't mutate the DB — long-form report tests, regression checks against a shared fixture, etc.

Combined with @Transactional on a service method, @ReadOnly also acts as a "discard everything" interceptor: writes that happen inside the method are reverted on return via the rollback-only marker. Useful for "what would happen if" probes that should not leave the DB mutated.

listing jpa-module/03 · readonlylistings/jpa-module/03-readonly/
// src/test/java/example/readonly/NoteService.java
@ApplicationScoped
public class NoteService {

    @Inject
    private EntityManager entityManager;

    @Transactional
    public Long persistNote(String text) {
        Note note = new Note(text);
        entityManager.persist(note);
        return note.getId();
    }

    /**
     * @Transactional @ReadOnly — the persist + flush succeed in-memory
     * during the method (so the id is assigned), but jpa-module's
     * interceptor marks the transaction rollback-only, so the row
     * never reaches the database.
     */
    @Transactional
    @ReadOnly
    public Long tryToPersistButDiscard(String text) {
        Note note = new Note(text);
        entityManager.persist(note);
        entityManager.flush();
        return note.getId();
    }

    @Transactional
    public long count() {
        return entityManager.createQuery("SELECT COUNT(n) FROM Note n", Long.class).getSingleResult();
    }
}

// src/test/java/example/readonly/ReadOnlyTest.java
@EnableTestBeans
@PersistenceConfig(persistenceUnitName = "notesPU")
class ReadOnlyTest {

    @Inject
    NoteService noteService;

    @Test
    void readOnlyPersistIsDiscardedAfterCommit() {
        Long assignedId = noteService.tryToPersistButDiscard("transient");
        assertThat(assignedId)
                .as("the persist+flush inside the method assigned an id (in-memory)")
                .isNotNull();
        assertThat(noteService.count())
                .as("after the method returns, the rollback discarded the row")
                .isEqualTo(0L);
    }

    @Test
    void plainTransactionalStillCommits() {
        noteService.persistNote("real");
        assertThat(noteService.count()).isEqualTo(1L);
    }
}

2.5 transaction events

Four CDI events fire around every transaction the strategy drives. Observe them with plain @Observes on a CDI bean for cross-cutting logging, audit trails, or cleanup of out-of-band resources:

  • TransactionStarted — right after begin() succeeds.
  • TransactionBeforeCompletion — before the strategy decides to commit or roll back. Last chance to flush or veto.
  • TransactionCommitted — after a successful commit.
  • TransactionRolledBack — after a rollback (whether explicit or exception-driven).

All four extend PersistenceUnitTransactionEvent so an observer that wants to react to "any transaction completion" can listen to the supertype.

listing jpa-module/04 · transaction-eventslistings/jpa-module/04-transaction-events/
// src/test/java/example/txevents/TransactionTimeline.java
@ApplicationScoped
public class TransactionTimeline {

    private final List<String> events = new CopyOnWriteArrayList<>();
    public List<String> events() { return events; }

    void onStart(@Observes TransactionStarted event) {
        events.add("start:" + event.getPersistenceUnitName());
    }

    void onCommit(@Observes TransactionCommitted event) {
        events.add("commit:" + event.getPersistenceUnitName());
    }

    void onRollback(@Observes TransactionRolledBack event) {
        events.add("rollback:" + event.getPersistenceUnitName());
    }
}

// src/test/java/example/txevents/TransactionEventsTest.java
@EnableTestBeans
@PersistenceConfig(persistenceUnitName = "notesPU")
class TransactionEventsTest {

    @Inject
    NoteService noteService;

    @Inject
    TransactionTimeline timeline;

    @BeforeEach
    void resetTimeline() {
        timeline.events().clear();
    }

    @Test
    void successfulTransactionFiresStartAndCommit() {
        noteService.persistNote("hi");
        assertThat(timeline.events()).containsExactly("start:notesPU", "commit:notesPU");
    }

    @Test
    void failedTransactionFiresStartAndRollback() {
        try {
            noteService.persistThenRollback("oops");
        } catch (RuntimeException expected) {
            // forced
        }
        assertThat(timeline.events()).containsExactly("start:notesPU", "rollback:notesPU");
    }
}

2.6 EmfCache

The EntityManagerFactory bootstrap is heavy (schema generation, metamodel build, connection-pool warm-up). Repeating it per test class would make a test suite of 200 classes take minutes longer than necessary. EmfCache stores the factories in a ConcurrentHashMap<String, EntityManagerFactory> keyed by PU name; the second test class to ask for notesPU reuses the first class's factory.

Cleanup is via a JVM shutdown hook registered on first use — every cached factory is closed in its own try/catch with WARN-level logs on failure. There's no explicit teardown API; the cache lives until the JVM exits.

3. spi / port reference

jpa-module ships seven ports in jpa-module/api, all prioritised SPIs (multi-impl, ordered by ServicePriorityResolver) discovered through ServiceLoader:

TransactionStrategy

The driver that the proxy-based @Transactional interceptor calls into. Default RESOURCE_LOCAL; jta-module ships a higher-priority JtaTransactionStrategy that wins when JTA is on the classpath. Override to plug a custom transaction manager (Bitronix, Spring's PlatformTransactionManager, …) into jawelte's test lifecycle.

DbCleanupStrategy

Drives the inter-method table wipe in in-memory mode. Default impl does TRUNCATE TABLE on every entity table the EntityScanner discovered, in reverse foreign-key order. Replace it for vendor-specific cleanup, soft-delete patterns, or to keep cleanup off for a specific PU.

TableNameResolver

Returns the list of database table names DbCleanupStrategy should wipe between methods. Default impl walks INFORMATION_SCHEMA.TABLES for the PUBLIC schema. Override to filter (exclude audit / lookup tables that shouldn't reset between methods) or to inject a custom-curated list.

listing jpa-module/05 · table-name-resolverlistings/jpa-module/05-table-name-resolver/
// src/test/java/example/tableresolver/SkipCleanupTableNameResolver.java
/**
 * Custom TableNameResolver impl that returns no tables — DbCleanupStrategy
 * therefore has nothing to wipe between methods. Result: data written
 * by one @Test method survives into the next.
 *
 * <p>@Priority lower than the framework default
 * (Integer.MAX_VALUE) wins the ServicePriorityResolver sort and
 * becomes the active impl.
 */
@Priority(1)
public class SkipCleanupTableNameResolver implements TableNameResolver {

    @Override
    public List<String> resolveTableNames(String persistenceUnitName,
                                          EntityManagerFactory entityManagerFactory) {
        return List.of();
    }
}

// src/test/resources/META-INF/services/org.os890.jawelte.module.jpa.api.port.TableNameResolver
example.tableresolver.SkipCleanupTableNameResolver

The default resolver carries no explicit @Priority (effective value Integer.MAX_VALUE); any registered alternative with a numerically-lower priority wins the ServicePriorityResolver sort and becomes the active impl.

EntityScanner

Walks the test classpath to discover @Entity classes for the active PUs. Default uses xbean-finder's annotation-index over the classpath roots; replace to plug in a Jandex index, a custom shaded scanner, or anything else fitting your build.

PersistenceUnitConnectionResolver

Maps a PU name to a JDBC Connection the cleanup strategy can use without going through JPA. Default opens a fresh connection per call against the PU's JDBC URL (H2 in-memory, by convention). Replace for connection-pool sharing or to redirect cleanup at a different DataSource.

PersistencePropertyResolver

Computes the Map<String, String> that's passed to Persistence.createEntityManagerFactory(name, props). Default mixes the H2 URL (in-memory or file-mode), Hibernate's dialect / DDL-generation settings, and any user persistence.xml properties. Replace to inject test-specific Hibernate flags (query-cache toggles, batching, stats).

CdiTransactionalSupportProvider

Bridges jawelte's TransactionStrategy into the CDI @Transactional interceptor. Used internally; you almost never replace this. Listed for completeness.
