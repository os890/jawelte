jaxrs-module starts a real HTTP server inside your test JVM, deploys a set of @Path-annotated resources you name on the test class, and hands you a Supplier<String> that returns the live base URL. Your test calls the endpoint over the wire exactly the way a remote client would — full HTTP round-trip, full provider chain, full status-code / header / body handling.

1. quick-start

1.1 purpose

Unit-testing a JAX-RS resource by calling its method directly works for the bean logic but skips the entire HTTP layer — status-code mapping, content negotiation, exception mappers, message-body readers/writers, security filters. jaxrs-module gives you that layer back: SeBootstrap wraps your @Path resources in a Jetty (CXF) or Undertow (RESTEasy) server bound to an OS-assigned port, your test makes a real HTTP call, and the assertions cover the same surface area a production client would see.

1.2 hello-world

One @Path resource in src/main, a test annotated @EnableJaxRs(restResources = {…}), an @Inject TestUrl field for the live base URL.

listing jaxrs-module/01 · hello-worldlistings/jaxrs-module/01-hello-world/
// src/main/java/example/jaxrs/HelloResource.java
@Path("/hello")
public class HelloResource {
    @GET
    public String hello() {
        return "hello, jaxrs-module";
    }
}

// src/test/java/example/jaxrs/HelloResourceTest.java
@EnableTestBeans
@EnableJaxRs(restResources = {HelloResource.class})
class HelloResourceTest {

    @Inject
    TestUrl testUrl;

    @Test
    void getHelloReturnsTheStubbedBody() throws Exception {
        HttpResponse<String> response;
        try (HttpClient client = HttpClient.newHttpClient()) {
            HttpRequest request = HttpRequest.newBuilder()
                    .uri(URI.create(testUrl.get() + "/hello"))
                    .GET()
                    .build();
            response = client.send(request, HttpResponse.BodyHandlers.ofString());
        }

        assertThat(response.statusCode()).isEqualTo(200);
        assertThat(response.body()).isEqualTo("hello, jaxrs-module");
    }
}

testUrl.get() returns the live http://localhost:{port} base URL the embedded server bound to. Concatenated with the resource's @Path it forms the request URI for any HTTP client (JDK's HttpClient here; JAX-RS's own ClientBuilder or another library works the same way).

1.3 maven setup

jaxrs-module's api / impl, jakarta.ws.rs-api, and a JAX-RS implementation. CXF here; RESTEasy works equally well.

pom.xml fragmentlistings/jaxrs-module/01-hello-world/pom.xml
<dependency>
  <groupId>org.os890.jawelte</groupId>
  <artifactId>jawelte-jaxrs-module-api</artifactId>
  <version>${jawelte.version}</version>
  <scope>test</scope>
</dependency>
<dependency>
  <groupId>org.os890.jawelte</groupId>
  <artifactId>jawelte-jaxrs-module-impl</artifactId>
  <version>${jawelte.version}</version>
  <scope>test</scope>
</dependency>
<dependency>
  <groupId>org.apache.cxf</groupId>
  <artifactId>cxf-rt-frontend-jaxrs</artifactId>
  <version>${cxf.version}</version>
  <scope>test</scope>
</dependency>
<dependency>
  <groupId>org.apache.cxf</groupId>
  <artifactId>cxf-rt-transports-http-jetty</artifactId>
  <version>${cxf.version}</version>
  <scope>test</scope>
</dependency>

2. detailed

2.1 @EnableJaxRs

@EnableJaxRs on the test class names the resource classes to deploy. Attributes:

  • restResources = {…} — the array of @Path-annotated classes that go into the deployment. Required; an empty array means "no resources" and is rarely useful.
  • applicationConfig = Application.class by default — a custom Application subclass can be plugged in for non-trivial deployments that need providers, exception mappers, etc.

The annotation is read once per test class; the server starts in beforeAll and shuts down in afterAll.

2.2 TestUrl

TestUrl is a Supplier<String> returning the base URL the embedded server bound to — typically http://localhost:{port} where {port} is OS-assigned (port 0). Inject it once per test class; concatenate with your resource paths to form the request URL.

2.3 ResponseDiff

ResponseDiff wraps a jakarta.ws.rs.core.Response and gives you fluent assertions on the status code, headers, and body. Useful when the test makes a JAX-RS ClientBuilder call and wants to assert on the resulting Response without manually pulling status / entity / Content-Type apart.

2.4 picking a JAX-RS implementation

jaxrs-module talks to JAX-RS through the standard SeBootstrap API, so any conformant implementation works. The two impls tested in jawelte's own sweep are Apache CXF (default; cxf-rt-frontend-jaxrs + cxf-rt-transports-http-jetty) and RESTEasy (resteasy-undertow et al). Pick by classpath dependency, no code change in the test.

3. spi / port reference

jaxrs-module ships no SPI / port of its own. The customization story is whatever SeBootstrap and the chosen JAX-RS implementation already expose. If you need to tweak the deployment (custom providers, JSON binding, security filters), do it via a custom Application subclass passed to @EnableJaxRs(applicationConfig = ...) — that's the standard JAX-RS extension point and jaxrs-module honors it as the override channel.
