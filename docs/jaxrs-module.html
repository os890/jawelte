jaxrs-module starts a real HTTP server inside your test JVM, deploys a set of @Path-annotated resources you name on the test class, and hands you a Supplier<String> that returns the live base URL. Your test calls the endpoint over the wire exactly the way a remote client would — full HTTP round-trip, full provider chain, full status-code / header / body handling.

1. quick-start

1.1 purpose

Unit-testing a JAX-RS resource by calling its method directly works for the bean logic but skips the entire HTTP layer — status-code mapping, content negotiation, exception mappers, message-body readers/writers, security filters. jaxrs-module gives you that layer back: Jakarta REST's standard SeBootstrap API (the Java-SE bootstrap entry-point added in JAX-RS 3.1) wraps your @Path resources in a Jetty (CXF) or Undertow (RESTEasy) server bound to an OS-assigned port, your test makes a real HTTP call, and the assertions cover the same surface area a production client would see.

1.2 hello-world

One @Path resource in src/main, a test annotated @EnableJaxRs(restResources = {…}), an @Inject TestUrl field for the live base URL.

listing jaxrs-module/01 · hello-worldlistings/jaxrs-module/01-hello-world/
// src/main/java/example/jaxrs/HelloResource.java
@Path("/hello")
public class HelloResource {
    @GET
    public String hello() {
        return "hello, jaxrs-module";
    }
}

// src/test/java/example/jaxrs/HelloResourceTest.java
@EnableTestBeans
@EnableJaxRs(restResources = {HelloResource.class})
class HelloResourceTest {

    @Inject
    TestUrl testUrl;

    @Test
    void getHelloReturnsExpectedBodyOverHttp() throws Exception {
        HttpResponse<String> response;
        try (HttpClient client = HttpClient.newHttpClient()) {
            HttpRequest request = HttpRequest.newBuilder()
                    .uri(URI.create(testUrl.get() + "/hello"))
                    .GET()
                    .build();
            response = client.send(request, HttpResponse.BodyHandlers.ofString());
        }

        assertThat(response.statusCode()).isEqualTo(200);
        assertThat(response.body()).isEqualTo("hello, jaxrs-module");
    }
}

testUrl.get() returns the live http://localhost:{port} base URL the embedded server bound to. Concatenated with the resource's @Path it forms the request URI for any HTTP client (JDK's HttpClient here; JAX-RS's own ClientBuilder or another library works the same way).

2. detailed

2.1 @EnableJaxRs

@EnableJaxRs on the test class names the resource classes to deploy. Attributes:

  • restResources = {…} — the array of @Path-annotated classes that go into the deployment. Required; an empty array means "no resources" and is rarely useful.
  • Providers (@Provider classes — exception mappers, filters, message-body readers/writers) belong in the same restResources array. The JAX-RS runtime inspects each class for its declaring annotation and dispatches accordingly. There is no separate "applicationConfig" attribute today; the restResources array is the entire deployment surface.

The annotation is read once per test class; the server starts in beforeAll and shuts down in afterAll.

registering a provider — ExceptionMapper

The restResources array accepts both @Path resources and @Provider classes (exception mappers, filters, body readers/writers). Same array, no separate attribute — the JAX-RS impl scans the array and treats each class according to its annotations.

listing jaxrs-module/02 · exception-mapperlistings/jaxrs-module/02-exception-mapper/
// src/main/java/example/exceptionmapper/TeapotException.java   (plain RuntimeException, no jawelte hook)
public class TeapotException extends RuntimeException {
    public TeapotException(String message) { super(message); }
}

// src/main/java/example/exceptionmapper/BrewResource.java   (the resource that throws)
@Path("/brew")
public class BrewResource {
    @GET
    public String brewCoffee() {
        throw new TeapotException("I'm a teapot");
    }
}

// src/main/java/example/exceptionmapper/TeapotExceptionMapper.java
@Provider
public class TeapotExceptionMapper implements ExceptionMapper<TeapotException> {

    @Override
    public Response toResponse(TeapotException exception) {
        return Response.status(418).entity(exception.getMessage()).build();
    }
}

// src/test/java/example/exceptionmapper/BrewResourceTest.java
@EnableTestBeans
@EnableJaxRs(restResources = {BrewResource.class, TeapotExceptionMapper.class})
class BrewResourceTest {

    @Inject TestUrl testUrl;

    @Test
    void mapperConvertsExceptionTo418() {
        try (Client client = ClientBuilder.newClient()) {
            try (Response response = client.target(testUrl.get() + "/brew").request().get()) {
                assertThat(response.getStatus()).isEqualTo(418);
                assertThat(response.readEntity(String.class)).isEqualTo("I'm a teapot");
            }
        }
    }
}

JAX-RS clients (the jakarta.ws.rs.client.Client family) live in cxf-rt-rs-client for the CXF stack; add it to the test classpath when the test makes outbound calls.

2.2 TestUrl

TestUrl is a Supplier<String> returning the base URL the embedded server bound to — typically http://localhost:{port} where {port} is OS-assigned (port 0). Inject it once per test class; concatenate with your resource paths to form the request URL.

2.3 picking a JAX-RS implementation

jaxrs-module talks to JAX-RS through the standard SeBootstrap API, so any conformant implementation works. Two impls are tested in jawelte's own sweep:

  • Apache CXF (default in every listing on this page): org.apache.cxf:cxf-rt-frontend-jaxrs + org.apache.cxf:cxf-rt-transports-http-jetty.
  • RESTEasy: org.jboss.resteasy:resteasy-undertow + org.jboss.resteasy:resteasy-core. Drop those onto the test classpath in place of the two CXF jars and the same listing code runs unchanged — jaxrs-module's SeBootstrap.start(...) picks whichever provider is on the classpath.

Pick by classpath dependency, no code change in the test.

2.4 ResponseDiff

ResponseDiff (org.os890.jawelte.module.jaxrs.api.ResponseDiff) wraps a jakarta.ws.rs.core.Response and gives you fluent assertions on the status code, headers, and body. Useful when the test makes a JAX-RS ClientBuilder call and wants to assert on the resulting Response without manually pulling status / entity / Content-Type apart.

listing jaxrs-module/03 · response-difflistings/jaxrs-module/03-response-diff/
// src/main/java/example/responsediff/OrderResource.java
@Path("/order")
public class OrderResource {

    @GET
    @Produces(MediaType.APPLICATION_JSON)
    public String getOrder() {
        return "{\"id\":1,\"name\":\"Widget\"}";
    }
}

// src/test/java/example/responsediff/OrderResourceTest.java   (test-class shape identical to listings 01/02)
@EnableTestBeans
@EnableJaxRs(restResources = {OrderResource.class})
class OrderResourceTest {

    @Inject TestUrl testUrl;

    @Test
    void responseBodyMatchesExpectedJson() {
        try (Client client = ClientBuilder.newClient()) {
            try (Response response = client.target(testUrl.get() + "/order").request().get()) {
                ResponseDiff.forJson(response)
                        .expectedContent("{\"name\":\"Widget\",\"id\":1}")   // different key order — still equal
                        .assertEquals();
            }
        }
    }
}

ResponseDiff bridges to content-diff-module — same semantic-equality rules, same ignoring() + unorderedArrays() tolerance knobs. Add content-diff-module-api/impl + Jackson + Jakarta-EL to the test classpath.

3. spi / port reference

jaxrs-module ships no SPI / port of its own. The customization story is whatever SeBootstrap and the chosen JAX-RS implementation already expose. For most cases (custom providers, exception mappers, JSON binding, security filters) the answer is to add the relevant @Provider classes to the restResources array on @EnableJaxRs; the JAX-RS runtime walks the array and dispatches each class according to its annotations.
