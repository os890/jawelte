spring-data-module is a single-jar CDI side-car. With it on the classpath, every interface that extends Spring Data's Repository (typically JpaRepository) becomes an injectable CDI bean — backed by the real Spring Data implementation, dispatching to jpa-module's transaction-scoped EntityManager. No Spring context, no @EnableJpaRepositories, no boilerplate per repository — the CDI extension does the wiring automatically.

1. quick-start

1.1 purpose

Spring Data is great at code-free repositories — declare an interface, get all the CRUD + query-derivation goodies. The problem is that Spring's own infrastructure for activating those interfaces assumes a Spring ApplicationContext. In a CDI test that's pure overhead. spring-data-module reads Spring Data's repository metadata, builds the real implementation through JpaRepositoryFactory, and registers it as a CDI bean — you get repository injection in a CDI test with no Spring boot infrastructure.

1.2 hello-world

One @Entity, one interface extending JpaRepository, one @Inject-and-use test method.

listing spring-data-module/01 · hello-worldlistings/spring-data-module/01-hello-world/
// CustomerRepository.java
public interface CustomerRepository extends JpaRepository<Customer, Long> {
}

// CustomerRepositoryTest.java
@EnableTestBeans
@PersistenceConfig(persistenceUnitName = "customersPU")
class CustomerRepositoryTest {

    @Inject
    CustomerRepository customerRepository;

    @Test
    @Transactional
    void savedCustomerIsRetrievable() {
        Customer saved = customerRepository.save(new Customer("Alice"));

        assertThat(saved.getId()).isNotNull();
        assertThat(customerRepository.findById(saved.getId()))
                .hasValueSatisfying(found -> assertThat(found.getName()).isEqualTo("Alice"));
        assertThat(customerRepository.count()).isEqualTo(1);
    }
}

No @EnableSpringData annotation, no @EnableJpaRepositories, no scan packages. Adding jawelte-spring-data-module to the test classpath is the entire opt-in.

1.3 maven setup

The single jar plus spring-data-jpa (consumers bring their own Spring Data version), on top of the usual jpa-module + CDI runtime stack. If you haven't set up jpa-module yet, do that first — see jpa-module · maven setup; spring-data-module reuses that EntityManager.

pom.xml fragmentlistings/spring-data-module/01-hello-world/pom.xml
<dependency>
  <groupId>org.os890.jawelte</groupId>
  <artifactId>jawelte-spring-data-module</artifactId>
  <version>${jawelte.version}</version>
  <scope>test</scope>
</dependency>
<dependency>
  <groupId>org.springframework.data</groupId>
  <artifactId>spring-data-jpa</artifactId>
  <version>${spring.data.jpa.version}</version>
  <scope>test</scope>
</dependency>
<!-- jpa-module already on the classpath supplies the EntityManager -->

2. detailed

2.1 discovery model

SpringDataRepositoryExtension is a CDI Extension discovered via META-INF/services/jakarta.enterprise.inject.spi.Extension. Its lifecycle phases:

  1. ProcessInjectionPoint — for every injection point in the deployment, the extension inspects the IP's declared type. If the type is an interface that transitively extends Repository and is not @NoRepositoryBean, it's added to the discovery set. (Using ProcessInjectionPoint rather than ProcessAnnotatedType is the right callback because repository interfaces are typically not in a bean archive under bean-discovery-mode="annotated" — ProcessAnnotatedType would never fire for them.)
  2. ProcessBean — accumulates every bean type the container processes, so the next phase can detect user-supplied producers and back off.
  3. AfterBeanDiscovery — for each discovered repository interface with no existing bean, registers a synthetic @RequestScoped CDI bean whose produceWith callback constructs JpaRepositoryFactory and returns factory.getRepository(repositoryInterface) — the same real implementation Spring Data ships.

The synthetic bean's types are exactly the discovered interface + Object. Framework super-interfaces (JpaRepository, CrudRepository, …) are not added as bean types, so the synthetic beans never compete on framework super-types when multiple repositories ship together.

derived query methods

The synthetic bean is the real Spring Data implementation, so all of Spring Data's query-derivation features are available — findByName(String), findByNameStartingWith(String), paged results, custom @Query JPQL/native, etc. The repository interface is the query DSL.

listing spring-data-module/02 · derived-querylistings/spring-data-module/02-derived-query/
// src/test/java/example/derivedquery/CustomerRepository.java
public interface CustomerRepository extends JpaRepository<Customer, Long> {

    Optional<Customer> findByName(String name);

    List<Customer> findByNameStartingWith(String prefix);
}

// src/test/java/example/derivedquery/DerivedQueryTest.java
@Test @Transactional
void findByNameExecutesAGeneratedQuery() {
    customerRepository.save(new Customer("Alice"));
    customerRepository.save(new Customer("Bob"));
    customerRepository.save(new Customer("Charlie"));

    assertThat(customerRepository.findByName("Bob"))
            .hasValueSatisfying(found -> assertThat(found.getName()).isEqualTo("Bob"));

    assertThat(customerRepository.findByNameStartingWith("C"))
            .extracting(Customer::getName)
            .containsExactly("Charlie");
}

2.2 @NoRepositoryBean opt-out

An interface annotated @org.springframework.data.repository.NoRepositoryBean is excluded from discovery. Use this for shared base interfaces — common reason: several JPA aggregate types that all need the same audit-style methods (id-keyed counts, soft-delete checks, …) and you want to declare those methods once. The base interface is marked @NoRepositoryBean so the extension doesn't try to register it directly; only the concrete subinterfaces become CDI beans.

listing spring-data-module/03 · no-repository-beanlistings/spring-data-module/03-no-repository-bean/
// src/test/java/example/norepo/AuditableRepository.java
@NoRepositoryBean
public interface AuditableRepository<T extends Auditable, ID> extends JpaRepository<T, ID> {
    long countAll();
}

// src/test/java/example/norepo/CustomerRepository.java
public interface CustomerRepository extends AuditableRepository<Customer, Long> {

    @Override
    @Query("SELECT COUNT(c) FROM Customer c")
    long countAll();
}

The concrete sub-interface (CustomerRepository) is auto-discovered and injectable. The base (AuditableRepository) is not — its only job is to share method signatures across multiple concrete repositories.

2.3 user @Produces back-off

If your test code (or another module) declares @Produces CustomerRepository — perhaps a Mockito mock for a unit test, or a custom factory for a multi-PU scenario — the extension's ProcessBean pass observes that bean and the AfterBeanDiscovery pass skips the synthetic registration for that interface. The user's producer wins. There is no on/off switch; it's pure observation.

The listing below skips Mockito and uses a tiny JDK-proxy producer so the example carries no matcher syntax — a static LAST_METHOD_CALLED field is the proof that the user producer (and not the synthetic one) served the injection.

listing spring-data-module/04 · user-produces-backofflistings/spring-data-module/04-user-produces-backoff/
// src/test/java/example/producesbackoff/CustomerRepositoryProducer.java
@ApplicationScoped
public class CustomerRepositoryProducer {

    public static final AtomicReference<String> LAST_METHOD_CALLED = new AtomicReference<>();

    @Produces
    @ApplicationScoped
    CustomerRepository produce() {
        InvocationHandler handler = (proxy, method, args) -> {
            LAST_METHOD_CALLED.set(method.getName());
            return method.getReturnType() == long.class ? 0L : null;
        };
        return (CustomerRepository) Proxy.newProxyInstance(
                getClass().getClassLoader(),
                new Class<?>[] {CustomerRepository.class},
                handler);
    }
}

// src/test/java/example/producesbackoff/UserProducesBackoffTest.java
@Test
void userProducerWinsOverSynthetic() {
    customerRepository.count();
    assertThat(CustomerRepositoryProducer.LAST_METHOD_CALLED.get()).isEqualTo("count");
}

2.4 @RequestScoped lifetime

The synthetic bean is @RequestScoped, which means consumers receive a CDI client proxy and the underlying JpaRepositoryFactory is materialised lazily on first method call — always inside a @Transactional or programmatic-transaction boundary where the EM proxy can resolve a live EntityManager.

Why request-scope, not application-scope: cdi-module's CdiTestBeanContainer activates a RequestContextController per test method, so each test gets a fresh factory. Any (theoretical) Spring Data metadata-cache mutation cannot leak between tests.

2.5 EntityManager dispatch & multi-PU caveat

The produceWith callback resolves the @Default EntityManager via CDI.current().select(EntityManager.class).get() — the per-call routing proxy registered by jpa-module-impl. Repository methods therefore participate in the caller's @Transactional boundary automatically.

Caveat — the default EM is always used. Multi-persistence-unit routing is not built in. Consumers with multiple PUs must supply their own @Produces CustomerRepository per repository, with a @PersistenceContext(unitName = "...") field for the right EM. The extension's @Produces-back-off rule then keeps your hand-written producer instead of registering a synthetic.

3. spi / port reference

spring-data-module ships no SPI / port of its own and no annotation surface. The user-facing api is exactly "extend JpaRepository and inject the interface". Customization happens through standard CDI:

  • Excluding an interface — annotate it @NoRepositoryBean.
  • Overriding a synthetic bean — declare your own @Produces CustomerRepository. The extension observes the user producer and skips the synthetic registration for that interface.
  • Targeting a non-default persistence unit — combine the above two: @NoRepositoryBean on the interface plus a hand-written producer with @PersistenceContext(unitName = "...").

The module does ship a ConfigKeyAliasProvider service for the unsatisfied-injection-point auto-mock filter — spring-data-module's framework-internal package prefixes are excluded so they don't show up as candidates for synthetic mocking. That's transparent to users; there's no knob to turn.
