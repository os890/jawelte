scope-module adds two CDI normal scopes tuned for tests — @TestMethodScoped (one bean instance per @Test method) and @TestClassScoped (one bean instance per test class). Put them on your beans and the framework destroys the old instance at the right boundary; no static-field gymnastics, no leaking state between methods.

Once on the classpath, scope-module also rebinds three jawelte concepts automatically: @SessionScoped beans behave like @TestMethodScoped, @ConfigBean classes behave like @TestClassScoped, and @TestBean static fields are @TestClassScoped. Auto-mocked beans (the default cdi-module output) drop from @RequestScoped to @TestMethodScoped too. The aim: nothing leaks between tests by default, and the user doesn't have to think about it.

1. quick-start

1.1 purpose

JUnit has two natural test boundaries — the test class (one per @BeforeAll / @AfterAll) and the test method (one per @BeforeEach / @AfterEach). Plain CDI doesn't give you scopes that map to either; @RequestScoped roughly tracks the test method (cdi-module activates a request around each one), and @ApplicationScoped covers the whole container's lifetime — which is the entire JVM under jawelte's per-class CDI bootstrap.

scope-module fills the gap. @TestMethodScoped reads as “application-scoped, but discarded between tests” — same proxy semantics, same lazy creation, but the bean instance is destroyed in afterEach. @TestClassScoped reads as “application-scoped, but discarded between classes” — destroyed in afterAll. Both contexts report isActive() == true for the whole CDI container's lifetime; bean access never throws ContextNotActiveException.

1.2 hello-world — @TestMethodScoped

Annotate a bean @TestMethodScoped, give it some mutable state, write two test methods that both touch it. State resets between methods.

listing 17 · test-method-scopedlistings/17-test-method-scoped/
// src/main/java/example/methodscope/Counter.java
@TestMethodScoped
public class Counter {

    private int value;

    public int increment() {
        return ++value;
    }
}

// src/test/java/example/methodscope/CounterTest.java
@EnableTestBeans
class CounterTest {

    @Inject
    Counter counter;

    @Test
    void firstMethodSeesFreshCounter() {
        assertThat(counter.increment()).isEqualTo(1);
    }

    @Test
    void secondMethodAlsoSeesFreshCounter() {
        assertThat(counter.increment()).isEqualTo(1);
    }
}

Both @Test methods increment exactly once and both see 1. Under @ApplicationScoped the second method would see 2; under @TestMethodScoped the bean is destroyed in afterEach and the next method gets a fresh instance.

1.3 @TestClassScoped — shared across methods

Swap the annotation, swap the assertion. Same bean lives for the whole class; increments accumulate.

listing 18 · test-class-scopedlistings/18-test-class-scoped/
// src/main/java/example/classscope/Counter.java
@TestClassScoped
public class Counter {

    private int value;

    public int increment() {
        return ++value;
    }
}

// src/test/java/example/classscope/CounterTest.java
@EnableTestBeans
@TestMethodOrder(MethodOrderer.OrderAnnotation.class)
class CounterTest {

    @Inject
    Counter counter;

    @Test
    @Order(1)
    void firstMethodIncrementsToOne() {
        assertThat(counter.increment()).isEqualTo(1);
    }

    @Test
    @Order(2)
    void secondMethodSeesTheSameCounterAtTwo() {
        assertThat(counter.increment()).isEqualTo(2);
    }
}

The @TestMethodOrder here is purely for asserting the second method's deterministic value; the lifetime claim itself doesn't depend on method order. Reach for @TestClassScoped when a fixture is expensive to build and you want it shared across all methods of one class — it's the framework-managed equivalent of a JUnit @BeforeAll + static field, with proper CDI lifecycle (@Inject, @PostConstruct, @PreDestroy).

1.4 maven setup

scope-module ships as an api / impl pair, same shape as the other modules.

pom.xml fragmentlistings/17-test-method-scoped/pom.xml
<dependency>
  <groupId>org.os890.jawelte</groupId>
  <artifactId>jawelte-scope-module-api</artifactId>
  <version>${jawelte.version}</version>
</dependency>
<dependency>
  <groupId>org.os890.jawelte</groupId>
  <artifactId>jawelte-scope-module-impl</artifactId>
  <version>${jawelte.version}</version>
  <scope>test</scope>
</dependency>

No surprises in the rest of the pom — it's the same stack as the core-docs listings (jawelte-core-api + impl, jawelte-cdi-module-api + impl, a CDI runtime, JUnit, AssertJ).

2. detailed

2.1 scope lifetime

Both scopes are normal scopes (proxy-based, lazy first-access creation, single managed instance per scope-store, passivating = false). The only difference from @ApplicationScoped is when the underlying instance is destroyed:

  • @TestMethodScoped — bean instance destroyed at the end of afterEach. @PreDestroy runs then. The proxy stays valid for the whole CDI container lifetime; the next test method's first access lazily allocates a fresh instance.
  • @TestClassScoped — bean instance destroyed at the end of afterAll. @PreDestroy runs after the user's own @AfterAll methods but before the CDI container shuts down.

Bean access never throws ContextNotActiveException; both contexts report isActive() == true for the whole CDI container's lifetime, allocating a fresh store between methods / classes as needed. This matters for libraries that probe BeanManager.getContext(...) — scope-module's contexts are always-on by design.

2.2 declarative remaps

scope-module ships three BeanScopeMapper providers (one of the core SPIs — see core docs section 3.5). Putting scope-module on the classpath turns these three remaps on automatically:

  • @SessionScoped → @TestMethodScoped. Web-tier @SessionScoped beans don't have a meaningful "session" inside a unit test — jawelte treats one test method as the analogue and rebinds the scope accordingly. Production code keeps @SessionScoped; the test runtime sees it as method-scoped.
  • @ConfigBean → @TestClassScoped. @ConfigBean is a stereotype that contributes @ApplicationScoped by default; with scope-module it becomes test-class-scoped instead, so config can drift across test classes without leaking.
  • @TestBean static-field → @TestClassScoped. The default scope for @TestBean static-field synthetic beans is @Singleton per the core docs; scope-module rebinds it to @TestClassScoped so the static-field instance is reset between test classes that share the JVM.

The remaps are unconditional — just having scope-module on the classpath is the trigger. If you want one of them off, ship your own higher-priority BeanScopeMapper (see the core docs' SPI section).

2.3 MP Config defaults

scope-module's META-INF/microprofile-config.properties sets three keys at MP Config ordinal 100. They're not your config — they're scope-module's contribution of friendly defaults to other modules' keys. Override any of them in a higher-ordinal source if you want different behaviour.

org.os890.jawelte.module.cdi.auto-mock.default-scope org.os890.jawelte.module.scope.api.TestMethodScoped

cdi-module's auto-mock scope key (see the cdi-module config). Without scope-module the auto-mock fallback is @RequestScoped; with scope-module on the classpath, auto-mocked beans are @TestMethodScoped — fresh per test method, destroyed at the end of afterEach.

org.os890.jawelte.module.wiremock.registry.default-scope org.os890.jawelte.module.scope.api.TestClassScoped

wiremock-module's WireMockServerRegistry scope key. WireMock servers are expensive to boot and reuse across methods of one class naturally; the test-class scope matches that pattern.

org.os890.jawelte.module.ejb.singleton.default-scope org.os890.jawelte.module.scope.api.TestClassScoped

ejb-module's mapping of @jakarta.ejb.Singleton. In a real EE container an EJB Singleton lives for the whole application; in a per-class CDI test the closest analogue is @TestClassScoped.

3. spi / port reference

scope-module ships no SPI / port of its own — the user-extensible surface is whatever core already defines. What scope-module does contribute lives entirely inside core's existing extension points:

  • Three ServiceLoader-registered BeanScopeMapper providers (the declarative remaps in section 2.2). Replace them by shipping your own higher-priority providers per the core SPI docs.
  • An MP Config defaults file at ordinal 100 (section 2.3). Override any key in a higher-ordinal source (system property, env var, your application's own microprofile-config.properties).
  • An internal TestModuleLifecyclePort impl that resets the per-method / per-class scope stores at the right boundary. Not user-facing.

If you want to add a custom scope of your own, the pattern is the same as scope-module itself: define an annotation meta-annotated with @NormalScope, ship a CDI Extension that registers the matching AlterableContext, and (optionally) ship a BeanScopeMapper to auto-rebind existing-annotation usages. Drop the result on the classpath and it's live.
